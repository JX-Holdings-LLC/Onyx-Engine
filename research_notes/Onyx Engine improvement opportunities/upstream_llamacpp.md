## 1. llama-server features Onyx lacks (what, flag/API, PR, maturity, adoption difficulty)

### Takeaway
The pinned tree's llama-server already has a large feature set Onyx has not reimplemented. It covers multi-strategy speculative decoding, host-RAM prompt caching with SWA/recurrent context checkpoints, a unified KV pool, slot save/restore, Prometheus metrics, `/slots`, sleep-on-idle, LoRA hot-swap, `/infill`, `/reranking`, Anthropic `/v1/messages`, the Responses API, router multi-model and more. The highest-value, lowest-cost gaps for a single-model engine are the host-RAM prompt cache with checkpoints, `/metrics`, slot save/restore and n-gram speculative decoding. Model-based speculative decoding (draft/MTP/EAGLE3/DFlash) is the biggest throughput win but also the biggest integration job.

### Inferences
Rough priority and difficulty for Onyx (single model, custom cpp-httplib server, JX Runtime parent):
- **Easy (days):** `/metrics` (Onyx already tracks timings; match the `llamacpp:*` names so existing dashboards and JX tooling work unchanged). `GET /slots`. `n_probs`/`post_sampling_probs` aliases on `/completion`. `return_tokens`, `t_max_predict_ms`, `id_slot` (Onyx already has slots). `/v1/messages/count_tokens` and the `input_tokens` endpoints.
- **Easy–medium:** slot save/restore/erase via `llama_state_seq_save_file/load_file` (or the `_ext` variants with flags for SWA models); `--sleep-idle-seconds` (tear down and recreate `llama_context`/model; JX Runtime may already handle idle unload by killing the process, so check that first); `/infill` (needs FIM tokens from the vocab: `llama_vocab_fim_pre/suf/mid`); `/reranking` (Onyx already has rank pooling, so this is mostly a route); LoRA hot-swap (`llama_adapter_lora_init` + `llama_set_adapters_lora`-style API; check the b8049 API shape).
- **Medium:** host-RAM prompt cache (`--cache-ram`) built on `llama_state_seq_get_data_ext`/`set_data_ext`, so slots can be evicted to RAM and restored by prefix match. This is the biggest multi-tenant latency win after LCP reuse. Context checkpoints are effectively **required** for correct prefix reuse on SWA (Gemma 3/4, gpt-oss) and recurrent/hybrid (Qwen3-Next, Mamba, Kimi) models. Without them Onyx's LCP reuse probably has to fall back to full re-prefill on those architectures. Also medium: an Anthropic `/v1/messages` translation layer and `/v1/responses` (upstream itself converts to chat completions, so Onyx can do the same in its HTTP layer); and reasoning-control.
- **Hard (weeks):** speculative decoding. The cheapest entry point is n-gram/self-speculative (`ngram-mod`, `ngram-simple`): no second model and good gains on code and repetitive output. Onyx could reuse `common/speculative.{h,cpp}` (`common_speculative_*`) rather than writing its own verifier, but must integrate draft and verify into its batched tick, handle per-slot rollback with `llama_memory_seq_rm`, and adapt logprobs. MTP/EAGLE3/DFlash need extra GGUF heads or draft models and interact with mtmd. Upstream needed many follow-up fixes (mtmd, SWA, slot save, logprobs, EOG), which signals the complexity.
- **Probably skip:** router/multi-model, built-in tools/MCP, web UI, `--connect`, `/v1/systemone`. JX Runtime already manages one process per model, so these duplicate its role.

### Gaps
- I did not read upstream `server-context.cpp` to measure how much code each feature needs; the difficulty estimates are judgement.
- I found no benchmarks in this pass quantifying speculative decoding speedups per strategy (PR descriptions likely have them, but I did not fetch them).

## 2. libllama / common / mtmd API changes a downstream must track, and churn rate

### Takeaway
libllama's C API keeps growing, with occasional hard breaks. Since the pin it gained a new batch/process API (`llama_batch_ext` + `llama_process`), MoE-cache params, graph-realloc stats and a version bump of state formats. The real breakage risk for Onyx is in `common/`: Onyx links `common_chat_*`, `common_sampler_*` and `common_batch_*`, and `common_chat_parse` and `mtmd_tokenize` signatures changed after the pin.

It adds `llama_context_params.samplers` (`llama_sampler_seq_config[]`, which must be sampler chains) and `llama_set_sampler(ctx, seq_id, smpl)`, with input allocation delegated to the scheduler ([#19266](https://github.com/ggml-org/llama.cpp/pull/19266)) and the adaptive-p sampler ([#17927](https://github.com/ggml-org/llama.cpp/pull/17927)). **[post-pin]**: the backend sampling graph is kept static across ubatches ([#30223](https://github.com/ggml-org/llama.cpp/pull/30223)), and greedy selection is used for eligible temp-0 chains ([#29797](https://github.com/ggml-org/llama.cpp/pull/29797)) — [llama.h](https://github.com/ggml-org/llama.cpp/blob/master/include/llama.h).
- Auto-fit params: `llama_params_fit` / `-fit on|off` (default on), `-fitt/--fit-target` MiB per device (default 1024), `-fitc/--fit-ctx` (default 4096 min ctx), from [#16653](https://github.com/ggml-org/llama.cpp/pull/16653) (2025-12-15) and the refactor [#22171](https://github.com/ggml-org/llama.cpp/pull/22171) (2026-04-21) — [README](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md).
- **[post-pin] `common/` breaks:** chat API refactor [#30210](https://github.com/ggml-org/llama.cpp/pull/30210) (2026-10-09) and "accumulate generated text and tokens as parse input" [#29876](https://github.com/ggml-org/llama.cpp/pull/29876). `common_chat_parse(const std::string&, ...)` became `common_chat_parse(const common_chat_input&, ...)`, `common_chat_template_direct_apply` now returns `common_chat_prompt`, and new types `common_chat_prompt`, `common_chat_input`, `common_chat_session` were added. Specialized parsers moved to `common/parsers` ([#27764](https://github.com/ggml-org/llama.cpp/pull/27764)), and a `common_schema` IR for JSON schema arrived ([#28736](https://github.com/ggml-org/llama.cpp/pull/28736)). In total `common/chat.h` changed by +166 lines and `common/common.h` by +184 — git diff pin..master.
- **[post-pin] mtmd API:** `mtmd_tokenize` now takes `const mtmd_context*` and `const mtmd_bitmap * const *` (source-compatible for most callers, but a signature change). New: `mtmd_tokenize_from_parts()` ([#28250](https://github.com/ggml-org/llama.cpp/pull/28250)), `mtmd_bitmap_init_lazy`, `mtmd_get_memory_usage`, and the `mtmd_audio_stream_*` streaming API ([#30629](https://github.com/ggml-org/llama.cpp/pull/30629)) — git diff of `tools/mtmd/mtmd.h`.
- Upstream added API/ABI compatibility checking: a script [#28579](https://github.com/ggml-org/llama.cpp/pull/28579) (2026-09-14), limited to libllama and libmtmd in [#30038](https://github.com/ggml-org/llama.cpp/pull/30038). `common/` is explicitly **not** covered.

### Inferences
- `include/llama.h` is relatively stable for Onyx's usage. Every function Onyx calls still exists at master, so a bump from b10711 should mostly compile. The breaks will come from `common_chat_parse` (now needs a `common_chat_input`, e.g. via `common_chat_input_tokenize` or the `common_chat_input(std::string)` constructor), from any `common_chat_templates_apply` result fields, and from sampler-init signature changes if Onyx builds samplers directly. Because the ABI checker excludes `common/`, expect `common/` to keep breaking without notice. One option is to pin a thin adapter layer in Onyx around `common_chat_*`.
- `llama_batch_ext` + `llama_process` looks like the future batch API, since upstream's own server has migrated. Onyx should plan to migrate eventually, though the legacy API is not deprecated yet.
- Backend sampling (on-GPU sampler chains via `llama_context_params.samplers`) is a possible throughput win for Onyx's batched loop. It avoids the full-vocab logits copy for greedy/top-k, but conflicts with Onyx's full-vocab softmax logprobs path, so it would have to be per request.

### Gaps
- I did not verify whether `common_sampler_init`'s signature changed between pin and master (I diffed `common/common.h` stats only, not `common/sampling.h`).
- The API changelog issue gives no dates, and its table lags actual changes.

## 3. Performance work (CPU, GPU backends, MoE offload, fit, quant types)

### Takeaway
Gains available to Onyx come mostly "for free" through ggml. Some, though, need Onyx to expose flags: `--fit` auto-params, `--n-cpu-moe`/`-ot`, the new `--moe-cache-mib` GPU cache for CPU-resident experts, `--n-cpu-ffn`, `--split-mode tensor`, `--lazy-mode`/`--load-mode`, `--repack`. Post-pin work is dominated by MoE kernels across CUDA/HIP/Vulkan/Metal/SYCL/OpenCL, Metal tensor-API flash attention and CPU tiled k-quant matmul.

### Cited Findings
- MoE offload: `-cmoe/--cpu-moe` ([#14992](https://github.com/ggml-org/llama.cpp/pull/14992), 2025-07-31), `-ncmoe/--n-cpu-moe N` ([#15077](https://github.com/ggml-org/llama.cpp/pull/15077), 2025-08-05), draft variants ([#15191](https://github.com/ggml-org/llama.cpp/pull/15191)), and `-ot/--override-tensor <regex>=<buft>`. **Older but essential for MoE.** Dense equivalent `-ncffn/--n-cpu-ffn N`: [#26622](https://github.com/ggml-org/llama.cpp/pull/26622) (2026-08-27) — [README](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md).
- **[post-pin]** MoE expert GPU cache: `--moe-cache-mib N` / `llama_model_params.moe_cache_size`, a device cache for experts kept in host memory, marked [EXPERIMENTAL] ([#29887](https://github.com/ggml-org/llama.cpp/pull/29887), 2026-10-07). Multi-GPU support in [#30112](https://github.com/ggml-org/llama.cpp/pull/30112); LRU replaced by a 50/50 SLRU in [#30637](https://github.com/ggml-org/llama.cpp/pull/30637) (2026-10-19).
- Auto-fit: `-fit` on by default since [#16653](https://github.com/ggml-org/llama.cpp/pull/16653), with `--fit-target` and `--fit-ctx`; OpenCL memory estimate [#22688](https://github.com/ggml-org/llama.cpp/pull/22688); SYCL fit-target [#27629](https://github.com/ggml-org/llama.cpp/pull/27629). - CPU: weight repacking (`--repack`, default on; Q4_0 → Q4_0_X_Y repack [#10324](https://github.com/ggml-org/llama.cpp/pull/10324), 2024); KleidiAI ([#11390](https://github.com/ggml-org/llama.cpp/pull/11390), 2025-02; v1.5.0 [#12568](https://github.com/ggml-org/llama.cpp/pull/12568)); AMX ([#8998](https://github.com/ggml-org/llama.cpp/pull/8998), 2024; moved to the CPU backend [#10570](https://github.com/ggml-org/llama.cpp/pull/10570)); automatic best-CPU-backend selection ([#10606](https://github.com/ggml-org/llama.cpp/pull/10606)). All **older**. **[post-pin]** tiled mul_mat for k-quants on CPU: [#27851](https://github.com/ggml-org/llama.cpp/pull/27851) (2026-09-26).
- Flash attention: `-fa on|off|auto` (default auto). **[post-pin]** Metal tensor-API FA kernels for F16 KV ([#29570](https://github.com/ggml-org/llama.cpp/pull/29570)) and BF16 ([#30491](https://github.com/ggml-org/llama.cpp/pull/30491)); Vulkan sparse FA for quantized K/V ([#29639](https://github.com/ggml-org/llama.cpp/pull/29639)); CUDA `GGML_FA_QUANTS` build control ([#28079](https://github.com/ggml-org/llama.cpp/pull/28079)).
- **[post-pin]** MoE kernels: CUDA fused weighted expert reduction ([#25952](https://github.com/ggml-org/llama.cpp/pull/25952)); Vulkan MoE-aware mat_mul_id tiles ([#29182](https://github.com/ggml-org/llama.cpp/pull/29182)) and topk_moe fusion for prefill ([#28422](https://github.com/ggml-org/llama.cpp/pull/28422)); Metal MoE + SSM_CONV fusion ([#28948](https://github.com/ggml-org/llama.cpp/pull/28948)); SYCL grouped MoE XMX GEMM ([#29245](https://github.com/ggml-org/llama.cpp/pull/29245)) and MXFP4 MoE ([#29809](https://github.com/ggml-org/llama.cpp/pull/29809)); HIP RDNA3.5 tile tuning ([#28195](https://github.com/ggml-org/llama.cpp/pull/28195), [#28935](https://github.com/ggml-org/llama.cpp/pull/28935)); OpenCL Adreno MoE kernels ([#30187](https://github.com/ggml-org/llama.cpp/pull/30187), [#30691](https://github.com/ggml-org/llama.cpp/pull/30691)); OpenVINO stateful decode ([#28638](https://github.com/ggml-org/llama.cpp/pull/28638)). KV cache types allowed: f32, f16, bf16, q8_0, q4_0, q4_1, iq4_nl, q5_0, q5_1 (`-ctk/-ctv`) — [README](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md).

### Inferences
- Bumping the pin picks up the backend and kernel work with no Onyx code changes. What Onyx needs to do is **plumb flags through `src/args.cpp`**: `--fit/--fit-target/--fit-ctx` (via `common_params` / `llama_params_fit`), `--n-cpu-moe`, `-ot`, `--moe-cache-mib`, `--n-cpu-ffn`, `--split-mode tensor`, `--load-mode`, `--lazy-mode`, `--repack`, `-ctk/-ctv`, `--swa-full`, `-kvu`. If Onyx parses args with upstream `common_params_parse` most of these come free. If it has its own parser (it has `args.cpp`), each is a small mapping to `llama_model_params`/`llama_context_params` fields or `tensor_buft_overrides`. Check `src/args.cpp` for which are already wired.
- `--fit` matters especially for JX Runtime, which spawns Onyx on arbitrary user hardware. Auto-selecting ngl/ctx to fit VRAM avoids OOM-on-start.

### Gaps
- I did not measure which perf flags Onyx already exposes (I did not read `src/args.cpp` in detail).
- No consolidated upstream benchmark numbers were collected for the post-pin perf PRs.

- Onyx uses `mtmd_helper_eval_chunk_single` per chunk. ## 5. Build number, release cadence, and distance behind b10711

### Takeaway
On 2026-10-21 the latest upstream tag is **b11766** (dated 2026-10-20), and `origin/master` is at `9a3b91c6` (2026-10-21). Onyx's pin, b10711 (commit 9723942a, 2026-08-30), is **1,071 commits / ~1,055 builds and ~7 weeks behind**. Upstream tags a build per merged commit, roughly 10–15 a day.

### Cited Findings
- Latest tags: b11766, b11765, b11763. b11766 is dated 2026-10-20; master head `9a3b91c6801e68f412fcf1b6f8e153aa562b8536` is dated 2026-10-21 — upstream git clone ([repo](https://github.com/ggml-org/llama.cpp/releases)).
- Pinned commit `9723942adc518b43c4b95dc4dce6906903eb5e09` ("hexagon: fix CPY fence bug (#28033)", 2026-08-30) is exactly tag b10711. `git rev-list --count pin..origin/master` = 1071 — upstream git clone.
- Tag dates: b6000 2025-07-27, b9000 2026-05-01, b10000 2026-07-14, b11000 2026-09-16, b11500 2026-10-08. Tags created per month: 2026-08 ≈309, 2026-09 ≈416, 2026-10 (1–20) ≈353 — upstream git tags ([releases](https://github.com/ggml-org/llama.cpp/releases)).
- An issue comment on [#9289](https://github.com/ggml-org/llama.cpp/issues/9289) (2026-10-10) proposes a "v0.6.0" entry. It is only a suggestion; I found no evidence that semantic-version releases have been adopted.

### Inferences
- At about 400 builds/month, a quarterly bump means about 1,200 builds of drift. Given the `common/` churn (e.g. the chat refactor #30210), smaller, more frequent bumps such as monthly ones would be cheaper. Each bump should be CI-tested against Onyx's `common_chat_*` and `mtmd_*` call sites. Upstream's new ABI-check script (#28579) can flag libllama/libmtmd breaks automatically, but not `common/` breaks.

### Gaps
- GitHub release-page metadata (binary assets, release notes) was not fetched; cadence is inferred from git tags.
- I found no official ggml.ai or Hugging Face blog posts from 2026 summarizing these features. The web search returned only third-party tutorials ([Spheron](https://www.spheron.network/blog/deploy-llama-cpp-server-gpu-cloud/), [Mintlify mirror](https://www.mintlify.com/ggml-org/llama.cpp/api/rest/overview)), which I did not rely on.
