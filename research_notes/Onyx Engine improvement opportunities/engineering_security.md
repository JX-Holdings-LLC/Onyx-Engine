# Engineering, Security, Testing and Distribution Practices for Onyx Engine (as of Oct 2026)

Repo baseline observed (local files, read 2026-10-21):
- `src/server.cpp` (cpp-httplib v0.54.1): binds `args.host` (default `127.0.0.1`); `OPTIONS .*` returns 403; a pre-routing handler **rejects any request carrying an `Origin` header** with 403; bearer auth via `req.get_header_value("Authorization") != expected` (plain `std::string` comparison, not constant-time); `/health` exempt; `set_read_timeout(600)` and `set_write_timeout(600)`; no `set_payload_max_length` call, so httplib's compiled default `CPPHTTPLIB_PAYLOAD_MAX_LENGTH` of 100 MB applies (`third_party/cpp-httplib/httplib.h:130`); no Host-header validation; default thread pool `max(8, hw_concurrency-1)`.
- `CMakeLists.txt`: static build, GGML_CUDA/VULKAN/METAL/HIP/BLAS options, `LLAMA_BUILD_SERVER OFF`, no sanitizer, clang-tidy or fuzz targets; GGML_RPC not enabled (upstream default OFF).
- llama.cpp pin: commit `9723942adc518b43c4b95dc4dce6906903eb5e09`, build `b10711` (`packaging/vendor/llama.cpp.conf`).
- `.github/workflows/release.yml`: 4 platforms (linux-x64 ubuntu-22.04, darwin-arm64, darwin-x64 macos-15-intel, win32-x64), CPU-only static builds with fixed AVX2/FMA/F16C flags on x64; `sha256sum` → `checksums.txt`; `softprops/action-gh-release` pinned by SHA; **no attestations, signing, notarization, or SBOM**. `actions/checkout@v4`, `actions/cache@v4`, `upload/download-artifact@v4` referenced by tag, not SHA.
- `ci.yml`: Linux/macOS build + `scripts/smoke-test.sh` (curl/python against a generated tiny random GGUF) + safetensors tests; Windows build-only. No sanitizer, fuzz, lint or perf jobs.
- `publish-vendor.yml` already uses `npm publish --provenance` with `id-token: write`.

## 1. Security of local LLM servers: CVEs, exposure incidents, and recommended defaults

### Takeaway
Most llama.cpp CVEs from 2024–2026 are memory-safety bugs in GGUF/tokenizer parsing (so a malicious model file is the main code-execution vector) and in the RPC backend. Onyx's pin (b10711) is newer than every fix build listed, and Onyx does not build RPC. Ollama's history shows the network-facing risks: DNS rebinding (CVE-2024-28224), very large numbers of internet-exposed unauthenticated instances, and a 2026 unauthenticated memory leak. Onyx already does better than llama-server or Ollama on Origin and CORS. Its remaining gaps are: no Host-header allowlist, a non-constant-time key compare, a 600 s read timeout that allows slowloris-style worker exhaustion, and an implicit 100 MB body limit.

### Cited Findings
**llama.cpp advisories (GitHub Security tab, first page of 10, more on page 2):**
- GHSA-3p4r-fq3f-q74v (2026-03-12, High): heap overflow from an integer overflow in the `mem_size` calculation, a **bypass of the CVE-2025-53630 fix**. GHSA-96jg-mvhq-q7q7 / CVE-2026-33298 (2026-03-18, High, CVSS 7.8): `ggml_nbytes` multiplies dims by strides without overflow checks, so a crafted GGUF gets an undersized allocation and a heap overflow. Fixed in build b7824. — [llama.cpp advisories](https://github.com/ggml-org/llama.cpp/security/advisories); [GHSA-96jg](https://github.com/ggml-org/llama.cpp/security/advisories/GHSA-96jg-mvhq-q7q7)
- GHSA-vgg9-87g3-85w8 (2025-07-10, High): integer overflow in the GGUF parser leading to heap out-of-bounds read/write (CVE-2025-53630). Also: GHSA-7rxv-5jhh-j6xx tokenizer signed/unsigned heap overflow (2025-06-23, High); GHSA-g4cc-763q-h9h6 heap over-read in `llama_model_load` (2025-06-25, Moderate); GHSA-8wwf-w4qm-gpqr buffer overflow through malicious GGUF vocab loading `token_to_piece` (2025-06-14, High). — [llama.cpp advisories](https://github.com/ggml-org/llama.cpp/security/advisories)
- GHSA-8947-pfff-2f3c / CVE-2026-21869 (2026-01-05): llama-server context-shift code used client-supplied `n_discard` without checking it is non-negative, giving an out-of-bounds write. Patched in commit c78fb90. The advisory text says Critical while the listing shows Low. — [GHSA-8947](https://github.com/ggml-org/llama.cpp/security/advisories/GHSA-8947-pfff-2f3c)
- GHSA-j8rj-fmpv-wcxw / CVE-2026-34159 (2026-03-26, Critical): unauthenticated RCE in the RPC backend's `deserialize_tensor()`, where `buffer==0` skips bounds checks on GRAPH_COMPUTE. Same root cause as 2024's CVE-2024-42478/42479 (GHSA-wcr5 write-what-where in `set_tensor`, GHSA-5vm9 arbitrary read in `get_tensor`). **Patched versions: "None"** in the advisory. — [GHSA-j8rj](https://github.com/ggml-org/llama.cpp/security/advisories/GHSA-j8rj-fmpv-wcxw)
- OSS-Fuzz has reported llama.cpp bugs, e.g. OSV-2024-1053, a heap-buffer-overflow read in `gguf_get_tensor_offset` (2024-09-13), filed under the "llamacpp" OSS-Fuzz package. — [OSV-2024-1053](https://db.gcve.eu/vuln/osv-2024-1053)
- llama.cpp's SECURITY.md: the private disclosure program is "disabled until further notice". DoS bugs are generally not treated as vulnerabilities. It says "Always execute untrusted models within a secure, isolated environment such as a sandbox" and "there are no reliable methods to detect malicious models". It advises not using RPC or llama-server on untrusted networks, verifying hashes of model weights, and having operators handle rate limits and resource controls. — [llama.cpp SECURITY.md](https://github.com/ggml-org/llama.cpp/blob/master/SECURITY.md)

**Ollama and exposure incidents:**
- CVE-2024-28224 (NCC Group, fixed in Ollama v0.1.29, 2024-03-14): DNS rebinding let a malicious web page drive the local unauthenticated API, read files and push them to an attacker registry. Recommended mitigations: **validate the Host header against an allowlist (for loopback services only `localhost` and loopback addresses, with port)**, require auth on any interface, and do not rely on DNS filtering. — [NCC Group advisory](https://www.nccgroup.com/research/technical-advisory-ollama-dns-rebinding-attack-cve-2024-28224/)
- Ollama's current `allowedHostsMiddleware` (server/routes.go, main): when bound to a loopback address it allows the Host only if it is empty, `localhost`, the machine hostname, `*.localhost`/`*.local`/`*.internal`, or an IP that is loopback, private, unspecified or local. Otherwise it returns 403. — [ollama routes.go](https://raw.githubusercontent.com/ollama/ollama/main/server/routes.go)
- Ollama binds 127.0.0.1:11434 by default. By default it allows CORS origins from 127.0.0.1/0.0.0.0, and `OLLAMA_ORIGINS` adds more. — [Ollama FAQ](https://docs.ollama.com/faq.md)
- Exposure counts differ by methodology. Cisco Talos (Shodan, Sep 2025) found more than 1,100 exposed Ollama servers, about 20% hosting accessible models. SentinelOne/Censys counted 175,000 exposed hosts, 48% with tool calling enabled. An Intruder/CSA scan (May 2026) found that about 31% of more than 5,200 Ollama APIs answered unauthenticated prompts. — [Cisco blog](https://blogs.cisco.com/security/detecting-exposed-llm-servers-shodan-case-study-on-ollama); [SC Media](https://www.scworld.com/brief/report-internet-exposed-ollama-ai-servers-widespread); [CSA research note](https://labs.cloudsecurityalliance.org/research/csa-research-note-exposed-ai-infrastructure-selfhosted-secur/)
- "Bleeding Llama" (Cyera): an unauthenticated memory leak in Ollama, fixed in 0.17.1 and tracked as CVE-2026-7482, reportedly affecting about 300,000 servers. The CVE was assigned late. — [NYU Shanghai RITS summary](https://rits.shanghai.nyu.edu/ai/bleeding-llama-critical-unauthenticated-memory-leak-hits-300000-ollama-servers/) (secondary source; primary Cyera write-up not fetched)
- CVE-2026-65105: NVIDIA NemoClaw launched Ollama bound to all interfaces instead of loopback, which a CSA note ties to DNS-rebinding and model-poisoning risk. This shows that a *wrapper's* launch flags can undo safe defaults, which is relevant to JX Runtime spawning Onyx. — [CSA NemoClaw note](https://labs.cloudsecurityalliance.org/wp-content/uploads/2026/09/CSA_research_note_nemoclaw_dns_rebinding_model_poisoning_20260905-csa-styled.pdf)

**How llama-server does it (for comparison):**
- llama-server's default `timeout_read`/`timeout_write` is 3600 s (`common/common.h`). Its API-key middleware accepts `Authorization: Bearer` or `X-Api-Key` and checks with `std::find` over the key list (plain equality, not constant-time). It has configurable CORS (`cors_origins`, including a `localhost` mode). HTTP threads are `max(n_parallel+4, hw-1)`, with a pool that can grow by up to 1024 dynamic threads. — [llama.cpp server-http.cpp](https://raw.githubusercontent.com/ggml-org/llama.cpp/master/tools/server/server-http.cpp); [common.h](https://raw.githubusercontent.com/ggml-org/llama.cpp/master/common/common.h)
- cpp-httplib v0.62.0 now bounds the whole request head (request line plus headers) by the read timeout instead of per read, explicitly "block[ing] slow-header workers". — [cpp-httplib v0.62.0](https://github.com/yhirose/cpp-httplib/releases/tag/v0.62.0)

### Inferences
- **GGUF parsing is Onyx's largest attack surface**, and it is inherited. Onyx loads one operator-chosen model, so the realistic threat is a user downloading a poisoned GGUF. Mitigations: stay current on the llama.cpp pin (the GHSA-3p4r bypass shows fixes can be incomplete); document that models are trusted input; optionally let JX Runtime verify model hashes before launch.
- Onyx's pin b10711 is numerically far past the fix builds cited (b7824 for CVE-2026-33298, ≤b7991 affected for the RPC bug). Onyx does not set GGML_RPC, so the unpatched RPC RCE does not apply. Recommend a CI assertion that `GGML_RPC` stays OFF.
- Onyx does not compile llama-server (`LLAMA_BUILD_SERVER OFF`). Server-specific CVEs like CVE-2026-21869 therefore do not apply directly. But Onyx reimplements context shift (`--context-shift`, `--keep`), so the *same class of bug* (unvalidated client-supplied counts and offsets) should be fuzzed and audited in Onyx's own code.
- **Rejecting every `Origin` header is stronger than Ollama's or llama-server's defaults** and blocks most browser-driven CSRF. It may not fully stop DNS rebinding: after rebinding the attacker page is *same-origin* with the server, and browsers generally omit `Origin` on same-origin GET requests. That would expose GET `/props` and `/v1/models` when no `--api-key` is set. (This is based on general Fetch-spec behaviour and was not verified against a specific source this session.) **Add a Host allowlist** on loopback binds, modelled on Ollama's middleware: `127.0.0.1`, `[::1]`, `localhost`, optionally with `:port`. When `--host` is non-loopback, require `--api-key` or print a loud warning.
- **Constant-time compare:** replace `!=` with a length-independent constant-time comparison, for example comparing SHA-256 digests of both strings with a XOR-accumulate loop, or OpenSSL's `CRYPTO_memcmp` (not linked here). A remote timing attack on loopback is low-risk, but the fix is about 10 lines and removes a code-review finding.
- **Timeouts and limits:** keep the write timeout long, since SSE streams can run for minutes. Cut the read timeout, which after the v0.62 upgrade also bounds headers, to something like 30–60 s. Set `svr.set_payload_max_length()` explicitly (for example 32–64 MB, or derive it from whether `--mmproj` is enabled) instead of relying on the implicit 100 MB. Consider capping concurrent connections and the thread pool relative to `-np`. Consider `set_keep_alive_max_count` / `set_keep_alive_timeout` (defaults 100 and 5 s).
- Treat the default bind as a contract: JX Runtime should never pass `--host 0.0.0.0` without an API key (the NemoClaw lesson). Onyx could refuse that combination unless an explicit `--allow-unauthenticated-remote` flag is set.

### Gaps
- Page 2 of llama.cpp advisories (older, 2023–2024) was not fetched. The GHSA-3p4r fix build was not retrieved because the fetch tool refused that page.
- I did not confirm from a primary source whether the current Ollama release still has any open exposure-class CVE, or read the Cyera primary write-up.
- No source was found on Wiz, Oligo or Trend Micro research specifically on llama.cpp-server exposure counts (as opposed to Ollama).

## 2. cpp-httplib status and alternatives

### Takeaway
cpp-httplib is very active. **v0.62.0 (19 Oct 2026)** is the latest, after eight releases since Onyx's v0.54.1 (30 Aug 2026), several of them hardening request smuggling, framing, Host handling and slow headers on the server side. Upgrade to v0.62.0, absorbing its breaking 400-on-missing-Host behaviour. Switching frameworks is not worthwhile: llama.cpp itself uses cpp-httplib, and Onyx uses none of the client or TLS code where many 2026 advisories live.

### Cited Findings
- cpp-httplib advisories in 2026 include: GHSA-jv63-rm9j-6jwc HTTP request smuggling via unconsumed GET body (2026-03-31, Moderate); GHSA-h6wq-j5mv-f3q8 DoS via negative chunk size (2026-05-12, Moderate); GHSA-xjxg-64p4-vj4m server-side header percent-decoding enabling CRLF injection (2026-05-12, High); GHSA-hg3g-vrg8-578g crash on malicious X-Forwarded-For under trusted-proxy config (2026-05-16, High); GHSA-2r2h-jc8w-w66c CRLF injection via trailer headers in chunked responses (2026-08-21, Moderate). Client-side or TLS-only: GHSA-6hrp (credential leak on redirect), GHSA-8ffh (TLS verification bypass on Mbed TLS/wolfSSL), GHSA-w7p7 (WebSocket TLS UAF), GHSA-22mf (cookie leak on redirect, 2026-09-30), GHSA-vq69 (CRLF in `open_stream`, 2026-10-02). The list has three pages; only page 1 was read. — [cpp-httplib advisories](https://github.com/yhirose/cpp-httplib/security/advisories)
- Releases after v0.54.1: v0.56.0 (11 Sep), v0.57.0 (21 Sep, rejects control chars in chunk-size lines to stop smuggling and bounds trailers), v0.57.1, v0.58.0 (26 Sep, rejected requests no longer leave partial data on the wire), v0.59.0 (3 Oct, rejects invalid Content-Length and control chars in request targets, escapes log data), v0.60.0/0.60.1, v0.61.0 (14 Oct, rejects multiple Host lines and invalid Host bytes), v0.62.0 (19 Oct). — [cpp-httplib releases](https://github.com/yhirose/cpp-httplib/releases)
- v0.62.0 breaking server changes: HTTP/1.1 requests without `Host` get 400; strict single-space request line; `#` in target gives 400; handler-set Content-Length/Transfer-Encoding are recomputed; request head bounded by read timeout as a whole; limit macros set to 0 mean unlimited; content setters replace existing Content-Type. Security fixes: strict RFC 9112 parsing, connection closes on ambiguous TE+CL framing, regex recursion stack overflow removed. — [v0.62.0 release](https://github.com/yhirose/cpp-httplib/releases/tag/v0.62.0)
- v0.61.0 Host validation only checks the byte set and duplicate lines. An empty Host or no Host line was still accepted in 0.61 (tightened in 0.62). — [v0.61.0 release](https://github.com/yhirose/cpp-httplib/releases/tag/v0.61.0)
- llama-server is built on cpp-httplib (`httplib::ThreadPool`, `set_pre_routing_handler`). — [server-http.cpp](https://raw.githubusercontent.com/ggml-org/llama.cpp/master/tools/server/server-http.cpp)

### Inferences
- The release pages omit the year, so the 2026 dating is inferred from the advisory dates (full dates) and ordering. Treat it as high-confidence, not verified.
- **Recommendation: bump to v0.62.0 now** and add a smoke test for the 400-on-missing-Host behaviour. curl always sends Host, so existing tests should pass. Check JX Runtime's Node proxy forwards Host. Then track httplib with the same automated pin-bump PR as llama.cpp (section 6). cpp-httplib is header-plus-source vendored, so a regex manager on `CPPHTTPLIB_VERSION` or a `third_party/cpp-httplib/VERSION` file works.
- Many 2026 httplib CVEs are client, TLS or WebSocket paths that Onyx never compiles or calls (`LLAMA_OPENSSL OFF`, no client use). Onyx's realistic exposure is the server parser: smuggling, CRLF, chunked DoS.
- Alternatives (Crow, Drogon, uWebSockets, Boost.Beast): I did not research their 2026 advisory or maintenance status this session. Reasoning only, not sourced: a switch would mean rewriting SSE streaming and the slot/backpressure glue, losing parity with upstream llama-server (which Onyx mirrors), and adding a heavier dependency (Boost; Drogon's trantor/jsoncpp). The benefit (async I/O) matters little for one model on loopback with `-np` usually ≤ 8. Only reconsider if Onyx needs HTTP/2, many thousands of concurrent streams, or if httplib maintenance stalls.

### Gaps
- No 2026 security or maintenance data gathered for Crow, Drogon, uWebSockets or Boost.Beast. Pages 2–3 of the cpp-httplib advisories were not read.

## 3. Testing: fuzzing, sanitizers, static analysis, API conformance, load/benchmark, golden outputs

### Takeaway
llama.cpp is in OSS-Fuzz and its GGUF parser keeps producing memory-safety CVEs. Onyx's own request-parsing code (JSON → params, media base64/data-URI decoding, tokenize/detokenize ids, logprobs, n_keep and context-shift arithmetic) has no fuzzing or sanitizer coverage today. Cheap, high-value additions: an ASan+UBSan CI job that runs the existing smoke test, a TSan job for the batching loop, libFuzzer harnesses for the request→params layer, clang-tidy, and a perf smoke check with llama-bench-style numbers or guidellm.

### Cited Findings
- llama.cpp is fuzzed in OSS-Fuzz ("llamacpp" package); e.g. OSV-2024-1053 heap overflow in `gguf_get_tensor_offset`. — [OSV-2024-1053](https://db.gcve.eu/vuln/osv-2024-1053)
- CVE-2026-21869 (unvalidated `n_discard` → OOB write in context shift) is the kind of bug that request-level fuzzing with sanitizers catches. — [GHSA-8947](https://github.com/ggml-org/llama.cpp/security/advisories/GHSA-8947-pfff-2f3c)
- cpp-httplib v0.62.0 notes include fixes to "ThreadSanitizer behavior", so TSan runs with httplib are a supported scenario. — [v0.62.0 release](https://github.com/yhirose/cpp-httplib/releases/tag/v0.62.0)
- GuideLLM (vLLM project) benchmarks any OpenAI-compatible HTTP server: `guidellm benchmark --target <url>`, auto-detects the model, rate types synchronous/throughput/concurrent, default sweep. Docs name vLLM and TGI; no explicit llama.cpp confirmation was found. — [GuideLLM docs](https://blog.vllm.ai/guidellm/main/getting-started/benchmark); [GuideLLM repo](https://github.com/vllm-project/guidellm)
- No widely adopted OpenAI-compat conformance suite exists. Closest leads: ModelRack (one conformance suite run against Ollama, generic OpenAI and llama.cpp adapters; small project) and the Llama Stack "verifications" suite (chat, image input, structured JSON output, tool calling, streaming and non-streaming). A 2026 Inworld guide lists the areas where compatibility diverges: streaming, tools, structured output, reasoning controls, usage fields, error handling, SDK behaviour. — [ModelRack](https://pypi.org/project/modelrack/); [Llama Stack verifications](https://git.kvant.cloud/phoenix-oss/llama-stack/src/tag/v0.2.4/tests/verifications); [Inworld guide](https://inworld.ai/resources/openai-compatible-inference-apis)

### Inferences
Concrete plan, ordered by value per effort:
1. **Sanitizer CI job (Linux, clang):** `-DCMAKE_BUILD_TYPE=RelWithDebInfo -DCMAKE_C_FLAGS/CXX_FLAGS="-fsanitize=address,undefined -fno-omit-frame-pointer"`, then run `scripts/smoke-test.sh` unchanged. The tiny random model keeps it fast. Add a second job with `-fsanitize=thread` exercising `-np 4` concurrent streams, because the single engine thread plus HTTP worker threads is where races live. Set `GGML_NATIVE=OFF` for reproducibility. Expect some ggml noise; suppress with UBSan/TSan suppression files for vendored code.
2. **libFuzzer harnesses (`fuzz/` dir, `-DONYX_FUZZ=ON`):** (a) chat/completions request JSON → internal params conversion, without a model, by refactoring parsing into a pure function; (b) `decode_media_payload` / base64 / data-URI parsing; (c) a GGUF-load harness, optional since upstream OSS-Fuzz covers it, but useful to exercise *Onyx's pinned* tree; (d) the safetensors converter, which is Python, so use atheris or Hypothesis there. Run each for about 60 s per PR, longer nightly. Keep a seed corpus from smoke-test requests. Upstream OSS-Fuzz enrolment needs a significant user base; ClusterFuzzLite (OSS-Fuzz-in-Actions) is the right-sized option. (Not verified this session.)
3. **clang-tidy and warnings:** `CMAKE_CXX_CLANG_TIDY` on `src/` only, with checks `bugprone-*`, `cert-*`, `clang-analyzer-*`, `performance-*`, `concurrency-*`. Add `-Wall -Wextra -Werror` on Onyx targets (llama.cpp's release uses `-DLLAMA_FATAL_WARNINGS=ON` — [llama.cpp release.yml](https://github.com/ggml-org/llama.cpp/blob/master/.github/workflows/release.yml)).
4. **OpenAI-SDK conformance tests:** run the official `openai` Python and Node SDKs against Onyx in CI (streaming, `stream_options.include_usage`, tool-call deltas, `response_format` json_schema, logprobs, embeddings, error shape). This directly protects JX Runtime's proxy. Reuse the Llama Stack verification categories as a checklist.
5. **Golden-output regression:** with a fixed seed, `temperature=0` and the deterministic tiny model, snapshot the token ids, logprobs and SSE frame sequence for a fixed prompt set. Fail on diff, and regenerate deliberately in llama.cpp-bump PRs. This catches tokenizer, template and sampler drift from upstream bumps. CPU-only and `GGML_NATIVE=OFF` are needed for bit-stability; cross-platform float differences may need per-platform goldens.
6. **Performance smoke:** a small real model (e.g. a Q4 ~0.5B, cached) on a self-hosted or nightly runner, with guidellm or k6/`vegeta` at fixed concurrency. Track tok/s and TTFT against llama-server at the same pin to catch regressions in Onyx's batching loop. Compare with upstream `llama-bench`, which is not built in Onyx (`LLAMA_BUILD_TOOLS OFF`), as the kernel-level baseline.
7. **Windows tests:** CI skips the smoke test on Windows. A minimal PowerShell or Python port of 5–10 checks would cover the shipped win32-x64 binary.

### Gaps
- I did not verify which fuzz targets llama.cpp currently registers in OSS-Fuzz, the ClusterFuzzLite setup details, or whether vLLM's `benchmark_serving.py` (now `vllm bench serve`) works cleanly against llama.cpp-style servers.

## 4. Release supply chain: provenance, signing, SBOM, notarization, Authenticode, reproducibility

### Takeaway
The cheapest big win is adding `actions/attest@v4` (build provenance plus SBOM attestation) to `release.yml` and turning on GitHub **immutable releases**. JX Runtime can then verify both with sigstore-js or by bundling `gh attestation verify --bundle` logic, on top of the existing `checksums.txt`. Apple notarization and Windows Authenticode (Azure Artifact Signing, about €8.60/mo) matter mainly when users run the binary outside JX Runtime's downloader. Treat them as second priority.

### Cited Findings
- GitHub artifact attestations: use `actions/attest@v4` with permissions `id-token: write`, `contents: read`, `attestations: write`, and `subject-path` set to the archive. For an SBOM attestation, generate the SBOM first (e.g. `anchore/sbom-action`) and pass `sbom-path`. Verify with `gh attestation verify PATH -R ORG/REPO`, plus `--predicate-type https://spdx.dev/Document/v2.3` for SBOMs. — [GitHub docs: use artifact attestations](https://docs.github.com/en/actions/how-tos/secure-your-work/use-artifact-attestations/use-artifact-attestations)
- Offline verification: `gh attestation download <artifact> -R ORG/REPO` produces a `.jsonl` bundle; `gh attestation trusted-root > trusted_root.jsonl`; then `gh attestation verify <artifact> -R ORG/REPO --bundle B.jsonl --custom-trusted-root trusted_root.jsonl`. Signing keys rotate several times a year, so the trusted root must be refreshed. Optionally pin `sourceRepositoryIdentifier` (repo ID) to defeat repo-rename reuse. — [GitHub docs: verify offline](https://docs.github.com/en/actions/how-tos/secure-your-work/use-artifact-attestations/verify-attestations-offline)
- Immutable releases (public preview Aug 2025): tags are locked to a commit, assets cannot be modified or deleted, and GitHub generates a signed release attestation (tag, commit SHA, assets). Verify with `gh release verify <tag>` and `gh release verify-asset <tag> <file>` (gh ≥ 2.81.0). Existing releases stay mutable unless republished. Verification proves membership in the release, not how it was built. — [GitHub docs: immutable releases](https://docs.github.com/en/code-security/concepts/supply-chain-security/immutable-releases); [changelog](https://github.blog/changelog/2025-08-26-releases-now-support-immutability-in-public-preview/); [verify release integrity](https://docs.github.com/en/code-security/how-tos/secure-your-supply-chain/secure-your-dependencies/verify-release-integrity)
- sigstore-js (`sigstore` / `@sigstore/verify` npm packages) can verify Sigstore bundles for arbitrary files. Pass the GitHub Actions issuer `https://token.actions.githubusercontent.com` and check the certificate SAN identity. `@sigstore/verify` 3.1.1 requires Node `^20.17.0 || >=22.9.0`. cosign ≥ 2.4.0 can verify GitHub Artifact Attestation bundles. — [sigstore JS docs](https://docs.sigstore.dev/language_clients/javascript/); [@sigstore/verify package.json](https://cdn.jsdelivr.net/npm/@sigstore/verify@3.1.1/package.json); [Sigstore blog](https://blog.sigstore.dev/cosign-verify-bundles/)
- llama.cpp's own release.yml (visible portion) showed no signing, attestation or SBOM steps. — [llama.cpp release.yml](https://github.com/ggml-org/llama.cpp/blob/master/.github/workflows/release.yml) (the file was truncated in the fetch, so this is not conclusive)
- Windows: Microsoft renamed Trusted Signing to **Artifact Signing**. `azure/artifact-signing-action@v2` uses OIDC (no stored secret) but runs **only on Windows runners**; `skeeto/aas-sign` is a cross-platform alternative. MSYS2 reports the basic tier at about €8.60/month, with one-time identity validation. — [Azure/artifact-signing-action](https://github.com/Azure/artifact-signing-action); [MSYS2 code signing](https://www.msys2.org/dev/code-signing/); [nullprogram, Apr 2026](https://nullprogram.com/blog/2026/04/25/)
- macOS: use `xcrun notarytool submit <zip> --keychain-profile … --wait` (altool is deprecated and no longer accepted). A bare Mach-O binary or a zip cannot be stapled, so Gatekeeper checks the ticket online on first run. Arduino CLI's pattern signs, notarizes, re-zips, then regenerates checksums. — [Apple: customizing the notarization workflow](https://developer.apple.com/documentation/security/customizing-the-notarization-workflow); [Apple forum thread](https://developer.apple.com/forums/thread/725942); [arduino-cli PR #578](https://github.com/arduino/arduino-cli/pull/578)
- Onyx's `publish-vendor.yml` already uses npm `--provenance` (local file), so the OIDC pattern is already familiar in the repo.

### Inferences
- **Minimal release.yml change:** in the `release` job, add `permissions: id-token: write, attestations: write`, then `actions/attest@v4` with `subject-path: dist/onyx-engine-*` (and `checksums.txt`). Add one SBOM step per platform (syft or anchore/sbom-action on the source tree, or a hand-written CycloneDX listing llama.cpp@commit and cpp-httplib@version, since syft cannot see vendored C++ well). Also pin `actions/checkout`, `cache`, `upload-artifact` and `download-artifact` by SHA, as is already done for softprops and ccache. Add `step-security/harden-runner` or at least review `permissions` per job. OpenSSF Scorecard would flag the tag-pinned actions (not fetched this session).
- **Signing order matters:** if macOS or Windows signing is added, it must happen *before* archiving, hashing and attesting, or checksums and attestations will cover unsigned bytes.
- **JX Runtime verification design:** (1) keep sha256 against `checksums.txt` as is; (2) additionally fetch the attestation bundle via the GitHub API (`GET /repos/{owner}/{repo}/attestations/sha256:{digest}`) and verify it with `@sigstore/verify`, pinning the certificate identity to `https://github.com/JX-Holdings-LLC/Onyx-Engine/.github/workflows/release.yml@refs/tags/v*` and the issuer to GitHub Actions. Ship a bundled trusted root with a refresh path. This upgrades "checksum from the same mutable release" to "binary built by this repo's release workflow from this tag". Immutable releases plus `gh release verify-asset` semantics close the "attacker with repo write access swaps assets and checksums.txt" gap.
- **Notarization is lower priority for JX Runtime's path.** Files written by Node's `fetch` plus `fs` do not normally get the `com.apple.quarantine` xattr (only quarantine-aware apps such as browsers set it), so Gatekeeper does not block them. This is an inference from macOS behaviour and was not verified against a source this session. Users who download the tarball manually in Safari or Chrome will hit Gatekeeper, so notarize when an Apple Developer account ($99/yr) is available. arm64 binaries are already ad-hoc signed by the linker.
- **Reproducible builds:** set `SOURCE_DATE_EPOCH`, `-ffile-prefix-map=$PWD=.`, `tar --sort=name --mtime=@$SOURCE_DATE_EPOCH --owner=0 --group=0 --numeric-owner` and `gzip -n` for archives. Pin runner images (`ubuntu-22.04` rather than `-latest`). This gives byte-reproducible Linux archives, which can be verified by rebuilding in a second workflow. macOS and Windows are harder; aim for Linux first.

## 5. Binary distribution: multi-backend builds, dynamic backend loading, more targets

### Takeaway
llama.cpp's own release ships CPU builds with `GGML_BACKEND_DL=ON` + `GGML_CPU_ALL_VARIANTS=ON` (runtime CPU-feature dispatch) and separate Vulkan, CUDA 12/13, ROCm, OpenVINO and SYCL variants. It also ships linux-arm64 and win-arm64. Onyx's single AVX2-hardcoded static binary will **SIGILL on pre-Haswell or AVX2-less x64 CPUs** and offers no GPU on Linux or Windows. The upstream pattern can replace it: a small `onyx-engine` executable plus `libggml-cpu-*.so` variants and optional GPU backend libraries, loaded with `ggml_backend_load_all()`.

### Cited Findings
- llama.cpp release matrix: macOS arm64 (`macos-26`, Metal embedded) and x64 (`macos-15-intel`); Ubuntu CPU x64/arm64/s390x; Ubuntu Vulkan x64/arm64; Ubuntu CUDA x64 (12.8.2 and 13.4.1) and arm64 (13.4.1), each with a separate CUDA runtime tarball (cudart, cublas, cublasLt); Android arm64; Windows CPU x64 **and arm64**; Windows ROCm/HIP x64 with a long gfx10/11/12 target list; OpenVINO. `GGML_BACKEND_DL` and `GGML_CPU_ALL_VARIANTS` are ON for the Ubuntu CPU/Vulkan/CUDA builds. Windows CPU x64 uses both; Windows arm64 uses BACKEND_DL with ALL_VARIANTS OFF; macOS uses neither. Flags include `-DGGML_NATIVE=OFF`, `-DCMAKE_INSTALL_RPATH='$ORIGIN'` / `'@loader_path'`, and `-DLLAMA_FATAL_WARNINGS=ON`. — [llama.cpp release.yml](https://github.com/ggml-org/llama.cpp/blob/master/.github/workflows/release.yml)
- Dynamic loading was introduced in llama.cpp PR #10469 ("ggml : add support for dynamic loading of backends"). CPU variant auto-selection came in #10606 ("automatic selection of best CPU backend"). Programs must call `ggml_backend_load_all()` before `ggml_backend_init_best()`, or no devices are found and ggml aborts on `GGML_ASSERT(device)` (a failure seen in Fedora's whisper.cpp packaging). CPU variant libraries are only found **next to the executable**, not via `LD_LIBRARY_PATH` (issue #17491). `GGML_BACKEND_PATH` env var loads an extra out-of-tree backend. — [PR #10469 commit](https://cdn04132025.gitlink.org.cn/replica/llama.cpp/commit/5931c1f233c616083d64e41a228249d58e039aa5); [#10606 commit](https://cdn04132025.gitlink.org.cn/replica/llama.cpp/commit/3420909dffa50e70660524797a1e715a717684d2); [Fedora whisper-cpp commit](https://http-dist-git.apps.ocp.stg.fedoraproject.org/rpms/whisper-cpp/commit/bf4fbcc5d24cc3ad6b97ff13d16a8f58e714ca2f); [llama.cpp issue #17491](https://github.com/ggml-org/llama.cpp/issues/17491); [GGML_BACKEND_PATH commit](https://cdn04132025.gitlink.org.cn/replica/llama.cpp/commit/c792dcf4880461c2b5f3960584db241ac71a893a)
- Onyx release flags (local): `-DGGML_AVX=ON -DGGML_AVX2=ON -DGGML_FMA=ON -DGGML_F16C=ON -DGGML_NATIVE=OFF` on linux-x64/darwin-x64; `-DGGML_AVX=ON -DGGML_AVX2=ON` on win32-x64; `BUILD_SHARED_LIBS=OFF`; Linux built on ubuntu-22.04, with an ldd check rejecting libgomp/libssl.

### Inferences
- **Option A (low effort):** keep static single-binary releases but add a `-noavx2` / baseline-SSE4.2 x64 variant. Alternatively, build static with `GGML_CPU_ALL_VARIANTS` if upstream supports static multi-variant (unverified; upstream ties ALL_VARIANTS to BACKEND_DL). Add `linux-arm64` (`ubuntu-24.04-arm` runners, as llama.cpp uses) and `win32-arm64` (`windows-11-arm`). Both match Node's `process.platform-process.arch` keys, which JX Runtime already uses.
- **Option B (upstream-aligned):** ship `onyx-engine` plus `libggml-base`, `libggml-cpu-{x64,sse42,haswell,skylakex,icelake,alderlake,zen4…}` and `libggml-vulkan` in a flat archive with `$ORIGIN` / `@loader_path` rpath. Call `ggml_backend_load_all()` at startup (or `ggml_backend_load_all_from_path(exe_dir)`). Report the loaded backends in `/props`. A Vulkan-enabled variant covers most Linux and Windows GPUs without CUDA licensing. Offer CUDA and ROCm as separate opt-in archives (`onyx-engine-<tag>-linux-x64-cuda12.tar.gz`), as llama.cpp does, with the CUDA runtime in a separate tarball because of size. This requires JX Runtime to understand a "variant" suffix in asset names and to keep sibling files together on extraction.
- Keep macOS as a single Metal-embedded static binary (upstream does the same).
- The ldd/otool dependency check should be extended to allowlist exactly the bundled `libggml-*` files when moving to Option B. Add a CI step that runs the binary on an old-ISA emulator (`qemu-x86_64 -cpu Nehalem` or Intel SDE) to prove there is no SIGILL.
- Static linking caveat: glibc static linking breaks NSS/`getaddrinfo`; the current dynamic glibc with a 22.04 baseline (glibc 2.35) is reasonable. Building in a manylinux-style older container (glibc 2.28) would widen compatibility to RHEL 8 and Debian 10.

### Gaps
- Not verified: whether `GGML_CPU_ALL_VARIANTS` works with `BUILD_SHARED_LIBS=OFF`; how Ollama, LM Studio or LocalAI package GPU variants in 2026; Vulkan backend stability on Windows/AMD for production.

## 6. Tracking a fast-moving upstream (llama.cpp pin bumps)

### Takeaway
Automate pin-bump PRs with a Renovate custom regex manager (`git-refs` datasource on `VENDOR_COMMIT` in `packaging/vendor/llama.cpp.conf`, or `github-releases` on the `bNNNN` tags), on a weekly cadence. Gate the PRs on the CI matrix plus golden outputs and an API-surface check of the `common/` and `llama.h` symbols Onyx uses. Ollama's documented process (manual pin, compat patches regenerated against a fresh checkout, diffing specific upstream paths, full multi-platform validation) is a good review checklist.

### Cited Findings
- Renovate regex managers need a `currentValue` or `currentDigest` named group, a `depName(Template)` and a `datasource(Template)`; RE2 regex (no lookahead or backreferences); matching is per file. — [Renovate regex manager](https://docs.renovatebot.com/modules/manager/regex/)
- `git-refs` datasource: capture the SHA as `currentDigest`, set `currentValueTemplate` to the branch (e.g. `master`), `packageNameTemplate` to the repo URL; it has no default versioning and no release timestamps. Example from the docs: `"matchStrings": ["GOOGLE_API_VERSION=(?<currentDigest>.*?)\\n"], "currentValueTemplate": "master", "packageNameTemplate": "https://github.com/googleapis/googleapis", "datasourceTemplate": "git-refs"`. — [Renovate git-refs datasource](https://docs.renovatebot.com/modules/datasource/git-refs/)
- Ollama's llama.cpp update process: pin with `LLAMA_CPP_VERSION`; CMake configure fetches and applies patches from `llama/compat/`; regenerate patches against a fresh checkout instead of editing `_deps/`; check whether upstream now natively supports a patched feature; review `git diff <old> <new> -- <path>` for build options, GGML/LLAMA symbols used by discovery code, llama-server flags and log lines, streaming behaviour, and model/tokenizer changes; then run `go test ./...`, a full release build, and per-platform integration tests that check device discovery, offload, memory accounting and flash attention. — [ollama llama/README.md](https://raw.githubusercontent.com/ollama/ollama/main/llama/README.md)

### Inferences
- **Renovate config sketch for Onyx** (untested; the per-file `^`/`$` semantics mean anchor on the literal key):
  ```json
  {"customManagers":[{"customType":"regex",
    "managerFilePatterns":["/^packaging/vendor/llama\\.cpp\\.conf$/"],
    "matchStrings":["VENDOR_COMMIT=\"(?<currentDigest>[0-9a-f]{40})\""],
    "currentValueTemplate":"master","depNameTemplate":"llama.cpp",
    "packageNameTemplate":"https://github.com/ggml-org/llama.cpp",
    "datasourceTemplate":"git-refs"}],
   "packageRules":[{"matchDepNames":["llama.cpp"],"schedule":["before 6am on monday"]}]}
  ```
  Caveat: `VENDOR_BUILD` and `VENDOR_UPSTREAM_VERSION` must change in lockstep, so a Renovate `postUpgradeTasks` script (self-hosted Renovate only) or a hand-written scheduled GitHub Action is probably simpler. The Action would resolve the latest `bNNNN` release tag via `gh api repos/ggml-org/llama.cpp/releases/latest`, rewrite all three keys, run `npm run vendor`, and open a PR with `peter-evans/create-pull-request`. Prefer tracking **release tags (`bNNNN`)** over `master` HEAD: they have passed upstream CI and map cleanly to `VENDOR_BUILD`.
- **API-break detection:** Onyx links `common` (Jinja templates, chat parsing, sampling), which upstream does not treat as stable API. In the bump PR, show `git diff old..new -- include/llama.h common/chat.h common/common.h common/sampling.h tools/mtmd/mtmd.h` in the PR body. Optionally run `abi-dumper`/`abi-compliance-checker` or a simple header-symbol grep against a list of symbols Onyx uses. Compile failure is the main signal; golden-output diffs (section 3) catch semantic drift.
- **Security-driven bumps:** subscribe to llama.cpp and cpp-httplib GHSA feeds (GitHub "Watch → Security alerts", or the OSV API in a scheduled job). Expedite a bump when an advisory touches `ggml/src/gguf.cpp`, `src/llama-vocab.cpp` or `common/`. Note that llama.cpp's private disclosure program is disabled and fixes land as public PRs, so watching merged PRs labelled security or touching gguf is the earliest signal. — [llama.cpp SECURITY.md](https://github.com/ggml-org/llama.cpp/blob/master/SECURITY.md)
- Keep zero local patches where possible (Onyx currently prunes but does not patch). If patches become necessary, follow Ollama's `compat/` model and regenerate them against a pristine checkout.
- Changelog hygiene: record the llama.cpp `bNNNN` and the cpp-httplib version per Onyx release in CHANGELOG.md and `/props`, so JX Runtime users can map CVEs to installed binaries. Onyx already exposes the pin in `--version` and `/props`.

### Gaps
- Did not verify how LM Studio (closed source) or llamafile (which carries a heavily patched llama.cpp fork) manage updates in 2026. Did not test the Renovate config. Dependabot has no generic regex manager (general knowledge, not fetched this session).
