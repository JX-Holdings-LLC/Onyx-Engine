# Onyx should mine its own pinned llama.cpp first

Most of what Onyx Engine needs to do its job better in late 2026 is already sitting in its own vendored tree. The pinned llama.cpp build (b10711, 2026-08-30) already ships a host-RAM prompt cache, context checkpoints for sliding-window and hybrid models, n-gram and MTP speculative decoding, `/metrics`, slot save/restore, `--fit` auto-sizing, MoE expert offload and Anthropic and Responses API routes. Onyx reimplements the server layer and has ported none of these ([server README](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md)). The most consequential gap is one Onyx's code imposes on itself. `src/engine.cpp` turns off KV prefix reuse entirely for any sliding-window or recurrent model ([src/engine.cpp](../src/engine.cpp), line 113). That covers most of the flagship families people run locally in 2026: Gemma 4, gpt-oss, the Qwen3.5 hybrids and Granite 4. On those models every chat turn re-prefills the whole transcript. The best value for effort comes from four kinds of change, in roughly this order. First, plumbing flags that libllama already supports: KV-cache type, MoE offload and auto-fit. Second, cheap operational endpoints and limits: `/metrics`, a queue cap that answers 503, a Host allowlist and an upgrade to cpp-httplib v0.62. Third, a host-RAM prompt cache with checkpoints. Fourth, translation layers for `/v1/responses` and `/v1/messages`, so that Codex and Claude Code work through JX Runtime. Speculative decoding is the biggest throughput lever but also the hardest integration, and n-gram drafting is the right first step. The safetensors converter needs a strategic rethink more than incremental fixes, because it converts almost no model in current use.

## Upstream already built most of Onyx's missing features

Most of the work is porting, not invention, and that framing changes the cost estimates. The research team diffed Onyx's pin against upstream `master`. The pin's own server README already documents `--spec-type ... draft-mtp,draft-dflash,ngram-*`, `--cache-ram`, `--kv-unified-per-slot`, `--fit`, `--sleep-idle-seconds`, `/v1/responses` and `/v1/messages`. **These are gaps in Onyx's server layer that need no pin bump.** Onyx links the same `llama.h`, so upstream's `tools/server` code is a working reference implementation built on the exact primitives Onyx already has. Today Onyx calls only `llama_memory_seq_rm/seq_add/seq_pos_min/clear/can_shift` and none of the `llama_state_*` functions that prompt caching and slot persistence are built on ([llama.h @ master](https://github.com/ggml-org/llama.cpp/blob/master/include/llama.h)).

The pin is also falling behind quickly. On 2026-10-21 the latest upstream tag was **b11766**, which puts Onyx **1,071 commits and about seven weeks behind**. Upstream cut about 416 tags in September 2026 alone ([llama.cpp releases](https://github.com/ggml-org/llama.cpp/releases)). The real breakage risk is in `common/`, not `llama.h`. Every libllama function Onyx calls still exists at master, and the legacy `llama_batch_init`/`llama_decode` path is not deprecated. After the pin, though, a chat API refactor changed `common_chat_parse` to take a `common_chat_input` and changed `common_chat_template_direct_apply` to return a new `common_chat_prompt` type ([#30210](https://github.com/ggml-org/llama.cpp/pull/30210)). Upstream added an API/ABI compatibility checker, but it explicitly covers only libllama and libmtmd and leaves `common/` out ([#28579](https://github.com/ggml-org/llama.cpp/pull/28579), [#30038](https://github.com/ggml-org/llama.cpp/pull/30038)). Onyx depends on `common_chat_*`, `common_sampler_*` and `common_batch_*` for templating, tool parsing and sampling ([docs/architecture/](../docs/architecture/README.md)), so it should expect silent `common/` breaks with every bump.

The practical answer is smaller and more frequent bumps that are tested automatically. At about 400 builds a month, a quarterly bump absorbs about 1,200 builds of drift. A scheduled GitHub Action is simpler than Renovate here, because `VENDOR_COMMIT`, `VENDOR_BUILD` and `VENDOR_UPSTREAM_VERSION` must change together. The Action would resolve the latest `bNNNN` tag, rewrite `packaging/vendor/llama.cpp.conf`, run `npm run vendor` and open a PR whose body diffs `common/chat.h`, `common/sampling.h` and `tools/mtmd/mtmd.h`. Renovate's regex manager with a `git-refs` datasource is an alternative ([Renovate git-refs](https://docs.renovatebot.com/modules/datasource/git-refs/)). Ollama's documented process makes a good review checklist for these PRs: diff specific upstream paths, check whether upstream now supports a patched feature natively, and run the full multi-platform validation ([ollama llama/README.md](https://raw.githubusercontent.com/ollama/ollama/main/llama/README.md)). Before the next bump, Onyx should also put a thin adapter around its `common_chat_*` call sites, so a refactor like #30210 touches one file. A post-pin change also matters to JX Runtime: upstream llama-server's **default port moved from 8080 to 9931** ([#30159](https://github.com/ggml-org/llama.cpp/pull/30159)). Onyx keeps 8080, which is fine, but any JX code that assumed parity with llama-server defaults should pass `--port` explicitly.

## Prefix caching is switched off for the models people actually run

The 2026 local model mix is dominated by architectures Onyx's cache cannot serve. Qwen3.5 interleaves Gated DeltaNet linear-attention layers with full attention at a **3:1 ratio** ([morphllm Qwen 3.5 guide](https://www.morphllm.com/qwen-3-5)). The Gemma 4 26B-A4B is a 128-expert MoE with a 1,024-token sliding window ([google/gemma-4-E2B card](https://huggingface.co/google/gemma-4-E2B)). The upstream converter now registers about 120 architecture modules, including Gemma 4, gpt-oss, DeepSeek V4, GLM-4.5/4.6, Kimi Linear, Granite 4 hybrids, Nemotron-H, Falcon-H1 and LFM2 ([llama.cpp conversion/](https://github.com/ggml-org/llama.cpp/tree/master/conversion)). Onyx's response to SWA or non-shiftable memory is to set `cache_reuse_ = 0` with a warning ([src/engine.cpp](../src/engine.cpp)). That is the safe choice, because a recurrent state cannot be truncated to an arbitrary position. The cost is that a growing chat transcript on these models gets **no prefix reuse at all**, and on CPU-bound hardware the wasted re-prefill is the dominant latency cost.

Upstream solves this with two mechanisms that compose, and both are portable. **Context checkpoints** (`--ctx-checkpoints`, 32 per slot by default, minimum step 8,192 tokens) periodically snapshot per-sequence state, so a later request can restore the nearest earlier checkpoint and decode only the suffix ([#15293](https://github.com/ggml-org/llama.cpp/pull/15293)). The **host-RAM prompt cache** (`--cache-ram`, 8 GiB default) keeps finished prompts in ordinary memory as "extra slots". It prefix-matches new requests against them and hot-swaps the best entry into the context. Its PR states that it works with a single slot and with dense, MoE, SWA and SSM models ([#16391](https://github.com/ggml-org/llama.cpp/pull/16391)). The underlying primitives are `llama_state_seq_get_data_ext`/`set_data_ext` with `SWA_ONLY` and `PARTIAL_ONLY` flags. The PR includes no benchmark of its own. A downstream project quoted on the PR page reported an **11.7k-token prompt dropping from 9.9 s cold to 0.97 s cached**, but that is an anecdote, not a controlled measurement. Upstream also landed several post-pin correctness fixes to SWA checkpoint invalidation and reuse thresholds ([#30666](https://github.com/ggml-org/llama.cpp/pull/30666), [#30580](https://github.com/ggml-org/llama.cpp/pull/30580)). Onyx should port this logic against a bumped pin rather than against b10711.

For Onyx specifically, the design follows from its existing slot model. On request completion, the engine would save the slot's sequence state to an LRU map keyed by `cache_tokens` under a byte cap. On admission, `admit_queued` already scans idle slots for the longest common prefix, and it would extend that scan to RAM entries. Checkpoints taken at fixed token intervals would make the same path work for SWA and hybrid models, which would let Onyx lift the blanket disable at line 113. Datacenter engines go further. SGLang's radix tree and vLLM's chained block hashes share physical KV between live sequences ([SGLang paper](https://arxiv.org/pdf/2312.07104); [vLLM prefix caching](https://docs.vllm.ai/en/latest/design/prefix_caching.html)). Those designs need paged KV that llama.cpp does not expose, so a per-sequence RAM cache is the right ceiling for Onyx. vLLM's idea of mixing an image hash into the cache key is worth borrowing, though. It is how Onyx could eventually re-enable caching under `--mmproj`, where it is currently force-disabled. Upstream still excludes mtmd from its RAM cache.

Three memory levers are pure flag plumbing and should ship first. **KV-cache quantization** (`--cache-type-k/-v`) maps directly onto `llama_context_params.type_k/type_v`. Ollama documents q8_0 as about half the memory of f16 with very small quality loss, and it requires flash attention ([Ollama FAQ](https://docs.ollama.com/faq)). One community benchmark found Qwen models below 0.04 KL divergence at q8_0, while a Gemma 26B-A4B variant at q4_0 reached **KL 1.088 with only 68% top-1 agreement** ([localbench](https://localbench.substack.com/p/kv-cache-quantization-benchmark)). Onyx should document q8_0 as the safe default and warn against q4_0 on SWA models. **MoE expert offload** (`--n-cpu-moe`, `--cpu-moe`, `-ot`) is the main way to fit 30B-plus MoE models on consumer GPUs ([#15077](https://github.com/ggml-org/llama.cpp/pull/15077)), and Onyx exposes neither, as its flag list in `src/args.cpp` confirms. **Auto-fit** (`--fit`, on by default upstream, with a 1,024 MiB per-device margin) picks the GPU layer count and context size to fit free VRAM ([#16653](https://github.com/ggml-org/llama.cpp/pull/16653)). That matters most for JX Runtime, which spawns Onyx on arbitrary user hardware, and today Onyx's only answer is `-ngl -1`. **Unified KV** (`kv_unified=true` with a per-slot cap) is the deeper fix for the README's admitted limit that `-np N` divides context N ways ([#24124](https://github.com/ggml-org/llama.cpp/pull/24124)). It is harder, though, because admission then has to check free cells rather than free slots.

## Scheduling and speculation: bound the tick before speeding it up

Onyx's engine loop already does the hard part of modern scheduling: it mixes prefill chunks with decode rows in one `llama_decode` per tick. What it lacks are the guardrails the field converged on. Sarathi-Serve's "stall-free" chunked prefill reports **up to 2.6x throughput within SLO** ([arXiv 2403.02310](https://arxiv.org/html/2403.02310v3)). vLLM V1 makes the pattern default: batch all decodes first, then fill a `max_num_batched_tokens` budget with prefill chunks ([vLLM optimization docs](https://docs.vllm.ai/en/v0.19.0/configuration/optimization/)). Onyx packs "a prompt chunk for each slot still prefilling" ([docs/architecture/](../docs/architecture/README.md)). If several slots prefill at once, the tick grows to the sum of their chunks, and every streaming client's inter-token latency suffers. An explicit per-tick token budget, decodes first, is a small scheduler change with a large effect on CPU hosts. Admission control is even cheaper. Onyx's queue is FIFO and unbounded, while Ollama returns **503 once 512 requests are queued** ([Ollama FAQ](https://docs.ollama.com/faq)). A `--max-queue` flag with `Retry-After` and a queue-wait timeout would give JX Runtime an overload signal it can act on. SGLang's cache-aware ordering, where a queued request with a long prefix hit may jump the FIFO head within a starvation bound, becomes worthwhile once the RAM cache exists.

Speculative decoding is still listed as out of scope in the README, but the ecosystem's evidence argues for a staged entry. Upstream's `--spec-type` now combines draft-model, EAGLE3, MTP, DFlash, DSpark and five n-gram strategies. The volume of follow-up fixes (EOG handling, mtmd, SWA, slot files, logprobs) signals real integration complexity ([#22673](https://github.com/ggml-org/llama.cpp/pull/22673), [#27196](https://github.com/ggml-org/llama.cpp/pull/27196)). Measured gains depend heavily on the workload. One HF benchmark at 128K context showed MTP adding only **+5% decode while costing 22% of prefill**, and n-gram caching *losing* 17% at 32% acceptance. It also reported that MTP silently disables parallel slots and cache reuse in llama.cpp ([HF Space benchmark](https://victor-mtp-on-hf-endpoints.static.hf.space/index.html)). Model-free suffix-based drafting shines on agent traffic: SuffixDecoding reports **1.8 to 4.5x on SWE-Bench/OpenHands traces** ([arXiv 2411.04975](https://arxiv.org/html/2411.04975v2)), and Snowflake measured 1.96 to 3.12x on an edit workload in production ([Snowflake](https://www.snowflake.com/en/engineering-blog/suffixdecoding-arctic-inference-vllm/)).

The right first phase for Onyx is n-gram/self-speculative drafting through upstream's `common_speculative_*`. It needs no second model, keeps parallel slots, and fits the single-batch design, because speculative rows are just extra rows for a slot's `seq_id`, with the rejected tail removed via `llama_memory_seq_rm`. It must be adaptive, disabling itself per slot when an acceptance EMA drops, or it reproduces the −17% case. MTP should wait, or be gated to `-np 1`, until upstream stops forcing a single slot. A separate draft model has only modest value on CPU-only machines, where both models compete for memory bandwidth.

Structured output has a similar "enable what is already there" option. llama.cpp's GBNF sampler is the slow baseline in the literature. llguidance computes masks in about 50 µs per token for a 128k vocabulary ([llguidance doc](https://huggingface.co/OpenTransformer/llama.cpp-prismml/blob/main/docs/llguidance.md)), and XGrammar reports up to 100x over the best baseline on context-free grammars ([arXiv 2411.15100](https://arxiv.org/pdf/2411.15100)). Mid-2026 head-to-heads between the two disagree ([arXiv 2608.12574](https://arxiv.org/pdf/2608.12574)). llama.cpp can be built with `LLAMA_LLGUIDANCE`, and that matters more in Onyx than elsewhere: sampling for all slots happens serially on one engine thread, so one slot's slow grammar mask delays every other slot's next token.

## Two translation layers would unlock today's agent clients

The OpenAI-compatible surface moved in 2026, and Onyx's endpoint table is a 2024 snapshot. The **Responses API** became the second table-stakes surface. The vendor-neutral Open Responses spec launched on 2026-01-15 with OpenRouter, Hugging Face, LM Studio, vLLM, Ollama and Vercel, and it ships conformance tests ([openresponses.org](https://openresponses.org/); [Simon Willison](https://simonwillison.net/2026/Jan/15/open-responses/)). Local servers implement a stateless subset. llama.cpp converts Responses requests into Chat Completions and rejects `previous_response_id` ([server-chat.cpp](https://raw.githubusercontent.com/ggml-org/llama.cpp/master/tools/server/server-chat.cpp)), and Ollama likewise supports "only the non-stateful flavor" ([Ollama OpenAI compatibility](https://docs.ollama.com/api/openai-compatibility)). Codex CLI compatibility drove upstream's work. The **Anthropic Messages API** followed the same path: llama.cpp, vLLM and Ollama all expose `/v1/messages`, mainly so Claude Code works by setting `ANTHROPIC_BASE_URL` ([HF blog](https://huggingface.co/blog/ggml-org/anthropic-messages-api-in-llamacpp); [Ollama Anthropic compatibility](https://docs.ollama.com/api/anthropic-compatibility)).

Both are medium-effort HTTP-layer work in `src/server.cpp`. Each needs a request converter into the existing chat path and a new SSE state machine. Responses streams require `sequence_number` and an `event:` name equal to the body `type`, and must end in `response.completed`/`failed`/`incomplete` ([Open Responses spec](https://www.openresponses.org/specification)). Anthropic streams need `message_start` through `message_stop`, `input_json_delta` for tool input and a `signature_delta` on thinking blocks ([Anthropic streaming docs](https://platform.claude.com/docs/en/build-with-claude/streaming)). Onyx has one differentiator to claim here. Ollama accepts Anthropic `budget_tokens` but does not enforce it, while Onyx's existing reasoning-budget machinery can. The Anthropic layer must also accept `x-api-key` alongside `Authorization: Bearer`. JX Runtime's `KIND_PATHS` currently forwards only chat, completion and embeddings ([docs/integration/jx-runtime.md](../docs/integration/jx-runtime.md)), so it would need new kinds too.

Several smaller compatibility fixes are cheap and remove real friction. On reasoning fields, vLLM renamed `reasoning_content` to `reasoning` and warns that the old field may come back empty ([vLLM reasoning outputs](https://docs.vllm.ai/en/latest/features/reasoning_outputs/)). Onyx should emit either field behind a switch, accept both on input, and parse top-level `reasoning_effort`, with `"none"` mapping to `enable_thinking=false` as llama.cpp, vLLM and Ollama all do. On embeddings, Onyx returns 400 for `dimensions` and for `encoding_format: "base64"` ([src/server.cpp](../src/server.cpp), lines 1193–1198), while llama.cpp accepts base64 ([server-context.cpp](https://raw.githubusercontent.com/ggml-org/llama.cpp/master/tools/server/server-context.cpp)) and Ollama accepts both. Truncating and renormalizing for Matryoshka models is a few lines of code. A Cohere/Jina-style `/v1/rerank` route over the existing `--pooling rank` path would turn a capability Onyx already computes into the API that Open WebUI-style RAG rerankers call. On tools, OpenAI's `allowed_tools` form of `tool_choice` and per-function `strict: true` are both enforceable through Onyx's existing grammar machinery ([OpenAI function calling](https://developers.openai.com/api/docs/guides/function-calling)). Ollama does not support `tool_choice` at all, so this is another place Onyx can be more reliable than the incumbent.

Observability is the cheapest high-value item in this whole report. Both reference servers expose Prometheus `/metrics`: llama.cpp with `llamacpp:*` counters and vLLM with TTFT, inter-token latency and queue-time histograms ([vLLM metrics](https://docs.vllm.ai/en/latest/design/metrics/)). The OpenTelemetry GenAI conventions define `gen_ai.server.time_to_first_token` and `time_per_output_token`, although they are still at Development stability ([OTel GenAI metrics](https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/gen-ai-metrics.md)). Onyx already computes `timings` and `cache_n` per request. Emitting them under llama.cpp-compatible names makes existing dashboards work unchanged, and an `X-Request-Id` echo would let JX correlate its logs with Onyx's. On readiness, Onyx's "listen only after load" design means JX cannot tell "still loading" from "crashed" except by timeout. llama.cpp's convention is to listen immediately and answer 503 `unavailable_error` while loading ([llama.cpp README](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md)). Adopting it would require a coordinated change to JX's `_waitReady()`, which today treats any response as ready. That makes it worth doing but not free. `/v1/models` should also carry the per-slot `n_ctx` and modalities that Onyx already reports in `/props`, since clients probe there for context length.

## Hardening and packaging gaps are small, cheap and concrete

Onyx's network posture is already stricter than its peers' in one respect: it rejects every request that carries an `Origin` header, which blocks most browser-driven CSRF ([src/server.cpp](../src/server.cpp), line 601). The gaps are the ones Ollama's history teaches. DNS rebinding (CVE-2024-28224) let a malicious page drive a loopback API, and NCC Group's mitigation was to **validate the Host header against a loopback allowlist** ([NCC Group](https://www.nccgroup.com/research/technical-advisory-ollama-dns-rebinding-attack-cve-2024-28224/)). Ollama now enforces exactly that ([routes.go](https://raw.githubusercontent.com/ollama/ollama/main/server/routes.go)). Browsers can omit `Origin` on same-origin GETs after a rebind, so without an `--api-key` Onyx's `/props` and `/v1/models` remain readable. That point rests on general Fetch-spec behaviour and has not been verified against a specific source. Exposure is not hypothetical. A May 2026 scan found that about 31% of more than 5,200 internet-facing Ollama APIs answered unauthenticated prompts ([CSA research note](https://labs.cloudsecurityalliance.org/research/csa-research-note-exposed-ai-infrastructure-selfhosted-secur/)). CVE-2026-65105 showed a *wrapper* (NVIDIA NemoClaw) undoing safe defaults by launching Ollama on all interfaces ([CSA NemoClaw note](https://labs.cloudsecurityalliance.org/wp-content/uploads/2026/09/CSA_research_note_nemoclaw_dns_rebinding_model_poisoning_20260905-csa-styled.pdf)). That is the exact relationship Onyx has with JX Runtime, so Onyx should refuse a non-loopback `--host` without `--api-key` unless an explicit opt-out flag is passed. The remaining fixes are each a few lines: a constant-time compare instead of `req.get_header_value("Authorization") != expected` (line 609), a read timeout well below the current 600 s, and an explicit `set_payload_max_length` instead of httplib's implicit 100 MB.

The HTTP library itself needs a bump. Onyx vendors cpp-httplib **v0.54.1**, and eight releases have shipped since. They harden request smuggling, chunk-size parsing, Host validation and slow-header handling, ending in **v0.62.0 (19 Oct 2026)**, which bounds the whole request head by the read timeout ([v0.62.0 release](https://github.com/yhirose/cpp-httplib/releases/tag/v0.62.0)). It brings a breaking change worth a smoke test: HTTP/1.1 requests without `Host` now get 400. Switching frameworks is not justified. llama-server itself runs on cpp-httplib, and many of the 2026 httplib advisories sit in client, TLS or WebSocket code that Onyx never compiles ([cpp-httplib advisories](https://github.com/yhirose/cpp-httplib/security/advisories)). Inherited model-file risk is real but already mitigated. GGUF parsing produced repeated integer-overflow CVEs in 2025–2026, including a bypass of an earlier incomplete fix, but all were fixed well before b10711 ([CVE-2026-33298](https://nvd.nist.gov/vuln/detail/CVE-2026-33298); [llama.cpp advisories](https://github.com/ggml-org/llama.cpp/security/advisories)). The RPC backend's critical RCE lists **no patched version** ([GHSA-j8rj](https://github.com/ggml-org/llama.cpp/security/advisories/GHSA-j8rj-fmpv-wcxw)). Onyx does not build RPC, and a CI assertion should keep it that way. Onyx reimplements context shift, and llama-server's CVE-2026-21869 was an out-of-bounds write from an unvalidated `n_discard` in that same code path ([GHSA-8947](https://github.com/ggml-org/llama.cpp/security/advisories/GHSA-8947-pfff-2f3c)). That is the strongest argument for adding an ASan+UBSan CI job that runs the existing `scripts/smoke-test.sh`, plus libFuzzer harnesses over request parsing and data-URI decoding.

Distribution has one latent crash and one cheap trust upgrade. The release workflow hard-codes AVX2/FMA/F16C on x64. Upstream instead ships `GGML_BACKEND_DL=ON` with `GGML_CPU_ALL_VARIANTS=ON` for runtime CPU dispatch, plus Vulkan, CUDA, ROCm and arm64 builds ([llama.cpp release.yml](https://github.com/ggml-org/llama.cpp/blob/master/.github/workflows/release.yml)). By that analysis, Onyx's binary will fault with SIGILL on AVX2-less x64 machines and offers no GPU on Linux or Windows. The low-effort fix is a baseline x64 variant plus `linux-arm64` and `win32-arm64`, all of which map onto the `${platform}-${arch}` keys JX already uses. The upstream-aligned fix is a small executable that ships beside `libggml-cpu-*` variants and a Vulkan backend. It must call `ggml_backend_load_all()`, and the variant libraries must sit next to the executable ([issue #17491](https://github.com/ggml-org/llama.cpp/issues/17491)). On supply chain, Onyx publishes `checksums.txt` from the same mutable release it checksums. Adding `actions/attest@v4` for build provenance and an SBOM, and turning on immutable releases, would let JX verify that a binary was built by this repo's workflow from a given tag ([GitHub artifact attestations](https://docs.github.com/en/actions/how-tos/secure-your-work/use-artifact-attestations/use-artifact-attestations); [immutable releases](https://docs.github.com/en/code-security/concepts/supply-chain-security/immutable-releases)). The repo already uses this OIDC pattern for npm `--provenance`. Windows Authenticode through Azure Artifact Signing costs about €8.60 a month ([MSYS2](https://www.msys2.org/dev/code-signing/)), and macOS notarization matters mainly for users who download outside JX.

## The converter covers almost nothing, so change strategy

The model-conversion story needs a decision more than a patch. Onyx's numpy-only converter accepts only `LlamaForCausalLM`. It raises on any `rope_scaling`, which the research notes say excludes Llama 3.1 and later. It also refuses every pre-tokenizer except plain `ByteLevel`, which excludes Llama 3's `Split`+`ByteLevel` tokenizer (`llama-bpe` upstream), and it writes no chat template ([scripts/convert-safetensors.py](../scripts/convert-safetensors.py); [convert_hf_to_gguf_update.py](https://github.com/ggml-org/llama.cpp/blob/master/convert_hf_to_gguf_update.py)). The notes read the code rather than running it against real checkpoints, but their conclusion holds up. Its real-world coverage is roughly Llama-2-era models and the repo's test fixture. Upstream identifies BPE pre-tokenizers by SHA-256 hashing token IDs from about 100 reference tokenizers ([conversion/base.py](https://github.com/ggml-org/llama.cpp/blob/master/conversion/base.py)), and keeping a hand-rolled converter in sync with that is not realistic.

A layered strategy keeps Onyx's zero-dependency principle while widening coverage. Pre-quantized GGUFs from ggml-org, Unsloth or bartowski should become the default path, through an `-hf repo:quant` resolver in JX or in Onyx that also pairs the matching `mmproj`, as upstream's `-hf` does ([docs/multimodal.md](https://github.com/ggml-org/llama.cpp/blob/master/docs/multimodal.md)). For the converter itself, Onyx can rebase onto the vendored `gguf-py`, which is numpy-only and version-matched to the pin ([gguf-py pyproject](https://github.com/ggml-org/llama.cpp/blob/master/gguf-py/pyproject.toml)). Its `SpecialVocab` already reads `chat_template.jinja`, and its quantizer can produce Q8_0, which would roughly halve the cached GGUF compared with the hard-coded f16 ([gguf-py quants.py](https://github.com/ggml-org/llama.cpp/blob/master/gguf-py/gguf/quants.py)). Two narrow fixes would make the existing Llama path useful: accept `rope_type: "llama3"`, and recognise the Llama 3 pre-tokenizer as `llama-bpe`. Everything else should fall back to upstream `convert_hf_to_gguf.py` when a torch environment is present, and should keep refusing clearly when one is not.

## Ranking the opportunities by value against effort

The table below orders recommendations by value per unit of effort. Effort estimates are judgement calls from the research notes, not measured code sizes.

| Priority | Change | Value | Effort | Where in Onyx |
|---|---|---|---|---|

## Conclusion

The research changes how Onyx's limits should be understood. The README's caveats about per-slot context splitting, no speculation and no RAM tier read like the inherent limits of a lean single-model server. In practice they are mostly unported upstream code that sits on primitives Onyx already links. The one limit that is truly self-imposed, disabling prefix reuse for SWA and recurrent memory, matters more each quarter, because new open-weight releases are overwhelmingly hybrid, sliding-window or MoE. That makes context checkpoints plus a RAM prompt cache the feature that most directly decides whether Onyx serves 2026 models well, ahead of any new endpoint.

The second implication concerns where Onyx's identity lies. Upstream llama-server keeps growing toward a router, agent runtime and web UI, and JX Runtime already owns process management and multi-model routing. Onyx's durable advantage is being the *narrow, hardened, well-instrumented* engine underneath: strict Origin and Host policy, enforced reasoning budgets, grammar-enforced `strict` tools and attested binaries. Matching upstream feature for feature is not the goal. Onyx should borrow llama-server's inference machinery aggressively, decline its platform ambitions, and invest in the bump-and-verify pipeline that keeps the two in step. Without that pipeline, every feature ported today becomes tomorrow's merge conflict in `common/`.
