# Cut common/ loose in four stages

Onyx can stop linking llama.cpp's `common/` library in roughly **9 to 14 engineer-weeks**. It does this by writing its own code for everything thin or churny and copying into its own tree the two hard, stable pieces it should not rewrite: upstream's Jinja engine and its JSON-schema-to-grammar converter. Everything Onyx needs exists in the public `llama.h`, `ggml-backend.h` and mtmd. That covers sampling, tokenizing, batching, MoE offload, the host-RAM prompt cache, context checkpoints, slot files and n-gram speculative decoding. mtmd already refuses to link `common/`, and libllama builds with `LLAMA_BUILD_COMMON=OFF` ([PIN CMakeLists.txt](https://github.com/ggml-org/llama.cpp/blob/9723942adc518b43c4b95dc4dce6906903eb5e09/CMakeLists.txt#L129); [tools/mtmd/CMakeLists.txt](https://github.com/ggml-org/llama.cpp/blob/9723942adc518b43c4b95dc4dce6906903eb5e09/tools/mtmd/CMakeLists.txt)). The chat layer (templating, tool-call and reasoning parsing) is the only large job, about 4 to 7 weeks, and it is the last tie to cut. Two things make the move worth it. Between the pin and master, `llama.h` changed almost entirely by addition (+120/−6 lines over 1,072 commits). Over the same span `common/` removed or reshaped functions Onyx calls ([llama.cpp](https://github.com/ggml-org/llama.cpp)). And most of the earlier report's biggest wins never touched `common/` in the first place: they are llama-server logic that Onyx ports onto `llama.h`. The honest costs are three. Onyx loses automatic support for brand-new chat templates. Auto-fit leans on an unstable staging header. And Onyx takes on two copied directories that it must watch for fixes.

## What to replace, copy or keep

The table below is the core of the answer. "Replace" means Onyx writes its own code on `llama.h`/ggml. "Copy" means Onyx vendors upstream source into its own tree, compiles it as Onyx code and pulls fixes deliberately. "Port" means Onyx re-implements logic from llama-server, which Onyx never links but uses as a reference. "Keep" means Onyx stays on upstream's library. Sizes and effort are the research team's estimates for one experienced C++ engineer; nothing was measured.

Three patterns run through the table. Almost every "Replace" verdict covers a thin layer: `common_sampler` only orchestrates samplers that libllama already exports, and libllama even keeps the penalty and DRY token history inside its own samplers ([PIN src/llama-sampler.cpp](https://github.com/ggml-org/llama.cpp/blob/9723942adc518b43c4b95dc4dce6906903eb5e09/src/llama-sampler.cpp#L2856-L2866)). The two "Copy" verdicts are the pieces where upstream's investment cannot be matched cheaply. Upstream's Jinja engine took 137 commits and still fails 14 of 370 templates ([PR #18462](https://github.com/ggml-org/llama.cpp/pull/18462)), and the schema converter has a 1,653-line test suite behind it ([PIN tests/](https://github.com/ggml-org/llama.cpp/tree/9723942adc518b43c4b95dc4dce6906903eb5e09/tests)). And the "Wait" verdicts all trace back to one file: `src/llama-ext.h`, which describes itself as a "staging header… everything here should be considered WIP" ([PIN src/llama-ext.h](https://github.com/ggml-org/llama.cpp/blob/9723942adc518b43c4b95dc4dce6906903eb5e09/src/llama-ext.h)).

## The staged plan to unlink common/

The order follows two rules. First, do the cheap removals that the next pin bump would force anyway. Second, front-load the work with the highest user value (prefix caching on SWA and hybrid models), and leave the long chat-layer job until last, because nothing else depends on it.

| Stage | What ships | Effort | Exit test | `common/` ties left |
|---|---|---|---|---|
| **1. Foundations** | `src/llama_util.*` (tokenize, batch, log); sampler wrapper; nlohmann swap with a depth cap; MoE flags and KV-type flags; the reuse-gate fix; the probe; a thin `src/chat/onyx_chat.h` seam over the existing `common_chat_*` calls | ~1–1.5 weeks | Same greedy output as today on the smoke test; grammar/tool tests pass | Chat layer, Jinja, schema converter |
| **2. Bump the pin, then KV state** | Pin bump (the seam absorbs the post-pin `common_chat_session` change); checkpoints; RAM prompt cache; slot files; media-aware matching. Auto-fit in parallel | ~2.5–3.5 weeks | Cached path gives the same tokens as a cold prefill on tiny dense, SWA and recurrent models, at `-np 1` and `-np 3` | Same |
| **3. Own the chat layer** | Copy Jinja and the schema converter; own render glue, parsers, reasoning, streaming and lazy grammars, family by family behind the seam with `--chat-backend=upstream` as fallback; then set `LLAMA_BUILD_COMMON OFF` | ~4–7 weeks (first useful milestone at ~2) | Golden renders for ~20 reference templates; each parser's streamed output equals its non-streamed output | **None** |
| **4. Speculation** | Verifier plumbing; adaptive n-gram drafting; `n_rs_seq` rollback for hybrid models. Draft-model mode afterwards, opt-in | ~1.5–2.5 weeks, plus 1–1.5 for the draft model | Bit-identical output at temp 0 with speculation on and off | None |

Stage 4 has no dependency on Stage 3, because it only needs the Onyx sampler from Stage 1. A second engineer could run it alongside the chat work. Stage 1 must land before the next bump. On master, `common_batch_add` and `common_batch_clear` are gone, replaced by a new `llama_batch_ext` API ([#29601](https://github.com/ggml-org/llama.cpp/pull/29601); [#24669](https://github.com/ggml-org/llama.cpp/pull/24669)), and the classic `llama_batch_init` path is still present. The KV work should be built against a bumped pin, not b10711. Several fixes that landed after the pin live inside libllama itself, not only in server logic. One is that `PARTIAL_ONLY` now honors its flag in the plain KV cache; at the pin, a "partial" save of a dense model returns the entire KV cache ([#30514](https://github.com/ggml-org/llama.cpp/pull/30514)). The others are a seq-state file version bump and cleanup after failed restores ([#28498](https://github.com/ggml-org/llama.cpp/pull/28498); [#27530](https://github.com/ggml-org/llama.cpp/pull/27530)).

Dropping `common/` also removes a build wart. Onyx's CMake currently orders its own httplib ahead of `llama-common`, because `llama-common` re-exports about 1,200 httplib symbols. cpp-httplib is "only used by common", so the ordering trick and the ODR worry both go away ([PIN vendor/CMakeLists.txt](https://github.com/ggml-org/llama.cpp/blob/9723942adc518b43c4b95dc4dce6906903eb5e09/vendor/CMakeLists.txt)). The `vendor::nlohmann` target is still built for mtmd even with `common/` off, but Onyx should keep its own copy in `third_party/` so that it owns the version.

## Small replacements are a day each

The sampler is the item most worth doing first, because once Onyx owns it, the grammar output from both the chat layer and speculation feeds Onyx code rather than `common_params_sampling`. The wrapper builds a chain with `llama_sampler_chain_init` and adds samplers in upstream's default order: logit bias (merged with `llama_vocab_get_suppress_tokens`), penalties, top-k, top-p, min-p and temperature. Identity samplers are skipped to save per-token work. The chain ends in `dist`, or in `greedy` when temperature is zero or top-k is 1, as master now does ([#29797](https://github.com/ggml-org/llama.cpp/pull/29797)). The grammar sampler is separate. The trick worth copying exactly is rejection sampling: apply the chain, check only the chosen token against the grammar using a one-element `llama_token_data_array`, and fall back to masking the full vocabulary only when that check fails ([PIN common/sampling.h](https://github.com/ggml-org/llama.cpp/blob/9723942adc518b43c4b95dc4dce6906903eb5e09/common/sampling.h#L10-L31)). This matters more in Onyx than upstream, because all slots sample on one engine thread and a full-vocab mask stalls every slot. Lazy triggers convert as upstream does. WORD triggers become regex-escaped patterns, PATTERN_FULL triggers are anchored with `^…$`, and TOKEN triggers go into the token list for `llama_sampler_init_grammar_lazy_patterns` ([PIN common/sampling.cpp](https://github.com/ggml-org/llama.cpp/blob/9723942adc518b43c4b95dc4dce6906903eb5e09/common/sampling.cpp#L188-L470)). The traps are small but real. The grammar must accept only generated tokens. The generation prompt is pre-fed only to non-user grammars. Construction must throw if the grammar fails to parse.

MoE offload is simpler than it looks. Upstream only builds `{regex, buffer type}` pairs such as `\.ffn_(up|down|gate|gate_up)_(ch|)exps` mapped to the CPU buffer type, and libllama does the `std::regex_search` during loading ([PIN common/common.h](https://github.com/ggml-org/llama.cpp/blob/9723942adc518b43c4b95dc4dce6906903eb5e09/common/common.h#L1127); [PIN src/llama-model-loader.cpp](https://github.com/ggml-org/llama.cpp/blob/9723942adc518b43c4b95dc4dce6906903eb5e09/src/llama-model-loader.cpp#L1231)). Onyx holds the pattern strings and the null-terminated override array in the engine for the model's lifetime, which avoids upstream's static-list leak. The tensor-name convention is informal, not an API, so the matching carries a little long-term risk.

Auto-fit is the one small item with an asterisk. Upstream's 1,072-line `common/fit.cpp` performs repeated trial loads with `no_alloc=true` and reads a per-buffer memory breakdown. It shrinks context first, then searches layer placement, keeping MoE dense weights on the GPU first ([PIN common/fit.cpp](https://github.com/ggml-org/llama.cpp/blob/9723942adc518b43c4b95dc4dce6906903eb5e09/common/fit.cpp#L178); [PR #16653](https://github.com/ggml-org/llama.cpp/pull/16653)). An Onyx version limited to one GPU plus CPU skips multi-GPU tensor splits and partial layers, which make up most of those lines. It needs only `ggml_backend_dev_memory` for free memory, and `llama_get_memory_breakdown`, which is exported from libllama but declared in the staging header. upstream's own mtmd helper includes that header too, and its memory-breakdown part did not change between the pin and master. If it disappears, the fallback is an estimate from GGUF tensor sizes plus a computed KV size, which is less accurate. Run fit before the engine thread starts, because it swaps the global logger. Turn it on only when `-ngl`, context size and overrides are all unset.

## KV state is a port of llama-server, not of common/

The prompt cache, checkpoints and slot files are the earlier report's most valuable items. They depend on `common/` only for a trivial helper. The upstream RAM cache is a `std::list` of `{tokens, checkpoints, state blob}`. It saves a slot's state only when the slot is about to be reused for a different prompt, either because it would keep less than half its tokens or because it was picked by LRU. It restores the cached entry that improves both the kept fraction and the similarity, skips entries below 25% kept, and erases the restored entry so a state is never held twice. It evicts oldest-first under byte and token caps ([PIN server-task.cpp](https://github.com/ggml-org/llama.cpp/blob/9723942adc518b43c4b95dc4dce6906903eb5e09/tools/server/server-task.cpp); [PIN server-context.cpp](https://github.com/ggml-org/llama.cpp/blob/9723942adc518b43c4b95dc4dce6906903eb5e09/tools/server/server-context.cpp)). Blobs are seq-id agnostic, so an entry from slot 2 restores into slot 0 ([PIN llama-kv-cache.cpp](https://github.com/ggml-org/llama.cpp/blob/9723942adc518b43c4b95dc4dce6906903eb5e09/src/llama-kv-cache.cpp)). In Onyx this slots into `admit()`: pick a slot (empty first, then LRU), save it if worth keeping, restore the best entry, then trim with `llama_memory_seq_rm`. No locking is needed, because the engine thread owns everything.

Checkpoints are what lift the blanket disable at [src/engine.cpp](../src/engine.cpp) line 113. Even before checkpoints exist, Onyx's gate is broader than upstream's. Upstream turns off only shift-based chunk reuse for non-shiftable memory and keeps plain prefix reuse. Onyx's `pos_min > 0` test rejects every valid SWA state once a conversation outgrows the window. A checkpoint is a `PARTIAL_ONLY` snapshot of just the state `seq_rm` cannot roll back: the SWA window or the recurrent state. It is taken before the prefill decode that crosses two boundaries, `n_prompt − 4 − n_ubatch` and `n_prompt − 4`. Upstream added those two end-of-prompt checkpoints because templates usually re-render the last assistant turn ([#20288](https://github.com/ggml-org/llama.cpp/pull/20288)). On admission, if `pos_min` is at or above the threshold, Onyx restores the newest valid checkpoint and re-prefills only the tail. Onyx must copy master's formulas, not the pin's. The pin's SWA threshold was off by two, and it rejected every state read back from the RAM cache or a slot file ([#30580](https://github.com/ggml-org/llama.cpp/pull/30580)). The pin also kept checkpoints built over a divergent history ([#30666](https://github.com/ggml-org/llama.cpp/pull/30666)). Those upstream bugs are effectively the risk catalogue for this stage, and every one is a silent wrong-output bug rather than a crash. That is why Stage 2's exit test compares the cached path against a cold prefill token for token.

Slot files should use an Onyx container rather than bare `llama_state_seq_save_file`. That function has no model-identity check, so a file from a different model with the same shape loads silently. Its version also changed after the pin, so a file never survives a bump ([PIN llama-context.cpp](https://github.com/ggml-org/llama.cpp/blob/9723942adc518b43c4b95dc4dce6906903eb5e09/src/llama-context.cpp)). An Onyx header carries a model fingerprint, the state version and length-prefixed checkpoint blobs. A mismatch is treated as a cache miss, not an error. The load path contains asserts, so slot loading should never be exposed without `--api-key`. Under `--mmproj`, reuse can come back by keeping media chunks in the token mirror, keyed by the SHA-256 id that mtmd's helper already assigns ([PIN mtmd-helper.cpp](https://github.com/ggml-org/llama.cpp/blob/9723942adc518b43c4b95dc4dce6906903eb5e09/tools/mtmd/mtmd-helper.cpp)). Positions must be tracked separately from token indices, and Onyx must never checkpoint inside a batch that contains media. Device-resident state (`ON_DEVICE`) is the wrong tool here. It keeps one snapshot per sequence and is used nowhere in upstream's server ([PIN llama.h](https://github.com/ggml-org/llama.cpp/blob/9723942adc518b43c4b95dc4dce6906903eb5e09/include/llama.h)).

## The chat layer is a hybrid: copied engine, owned parsers

This is where "at least as good" needs care. Upstream's chat stack is about 17.8k lines at the pin. It has an in-house Jinja engine, string-sniffing detection for about 20 model families, a generic "autoparser" that renders a template differentially to infer its format, and a PEG parser that also emits the tool-call grammar ([PIN common/chat.cpp](https://github.com/ggml-org/llama.cpp/blob/9723942adc518b43c4b95dc4dce6906903eb5e09/common/chat.cpp)). It churns hard. In seven weeks `chat.cpp` shrank from 3,915 to 1,782 lines, a new `parsers/` directory appeared, and `common_chat_parse` changed signature ([PR #30210](https://github.com/ggml-org/llama.cpp/pull/30210)). The Jinja engine, by contrast, grew only about 4% ([MASTER common/jinja/](https://github.com/ggml-org/llama.cpp/tree/339f3242c761f16c27e5ffcde1d35dcc31933a55/common/jinja)). So Onyx should copy the stable engine and own the churning glue.

Writing a new Jinja subset is the clearest "takes long and ends up worse" case. A census of 75 real templates finds the "subset" still needs macros, `namespace`, slicing, about 15 filters, a dozen string methods, loop variables, whitespace control and Python-compatible `tojson` ([MASTER models/templates/](https://github.com/ggml-org/llama.cpp/tree/339f3242c761f16c27e5ffcde1d35dcc31933a55/models/templates)). minja is the only drop-in alternative, and it has been effectively orphaned since September 2025 ([google/minja](https://github.com/google/minja/blob/021c2293c187789ef13d56c6cfd89c9b134fd80f/README.md)). Ollama's hand-written renderers avoid Jinja entirely, but its Gemma 4 renderer alone is about 840 lines of Go, and the approach breaks `--chat-template` overrides and `chat_template_kwargs` ([ollama renderers](https://github.com/ollama/ollama/blob/2cd63f7a15039ccd790e97b31edc091fa1707c56/model/renderers/renderer.go)). The copied engine keeps upstream's input marking, which stops special tokens being injected through user content ([PIN common/jinja/README.md](https://github.com/ggml-org/llama.cpp/blob/9723942adc518b43c4b95dc4dce6906903eb5e09/common/jinja/README.md)).

On the output side, Onyx should follow the vLLM and mistral.rs shape: an explicit registry of parsers chosen by sniffing the template, with a `--tool-parser` override. Each independent project lands on a similar list, roughly 20 in Ollama, 9 formats in mistral.rs and 53 tool parsers in vLLM ([ollama parsers.go](https://github.com/ollama/ollama/blob/2cd63f7a15039ccd790e97b31edc091fa1707c56/model/parsers/parsers.go); [mistral.rs parsers](https://github.com/EricLBuehler/mistral.rs/blob/4c56e256dea8fa61f7457aedacc6ce5a96a4ffdd/mistralrs-core/src/tools/parsers/mod.rs); [vLLM tool_parsers](https://github.com/vllm-project/vllm/tree/7e3d55956577605838e9babcba84dce354b0b78c/vllm/tool_parsers)). For the families that matter, about nine formats cover it. Tagged JSON (Hermes/Qwen3, which doubles as the fallback), Qwen3-Coder XML (also used by Qwen3.5 and Nemotron 3 Nano), Llama 3, Mistral `[TOOL_CALLS]`, Harmony (gpt-oss), DeepSeek, GLM, Kimi and Gemma 4. On top of those sit about four reasoning conventions. Each parser is a streaming state machine with `feed()` and `finish()`. It holds back only a suffix that could start a delimiter, matches on token ids where delimiters are special tokens, and appends argument bytes without ever retracting them. That is more robust than upstream's pin-era approach of re-parsing the whole output on every token, which throws if the tool-call count shrinks ([PIN common/chat.cpp L266-L320](https://github.com/ggml-org/llama.cpp/blob/9723942adc518b43c4b95dc4dce6906903eb5e09/common/chat.cpp)). Each parser also emits its own lazy grammar: its opening delimiter as a trigger, plus per-tool alternatives whose arguments come from the copied schema converter.

The loss must be stated plainly. Without the autoparser, a never-before-seen template produces content-only output with no tool calls until someone adds a parser. Community model cards already describe that failure on older llama.cpp builds ([HF model card](https://huggingface.co/Moore2877/Qwen-Agentic-Chat-Template-llamacpp)). The mitigations are the tagged-JSON fallback, the CLI override and a loud warning. The strongest alternative is to keep upstream's chat layer behind the Stage 1 seam permanently. That costs about 3 to 5 days once, plus 0.5 to 2 days per pin bump, and gives the best day-one coverage of new models. If the owner values day-one support for new families more than fewer dependencies, that is the right call. Stage 3 can then stop after the copies, at the cost of keeping `common/` linked.

## Speculation is owned in two stages, MTP waits

Speculative decoding needs nothing outside `llama.h`. For a draft of length k, Onyx adds k+1 rows for the slot's `seq_id`: the last sampled token plus the drafts, all with logits on. After the shared `llama_decode` it samples left to right with the slot's own chain and stops at the first mismatch, so every step yields at least one token. It then trims the rejected tail with `llama_memory_seq_rm` ([PIN common/sampling.cpp L678–706](https://github.com/ggml-org/llama.cpp/blob/9723942adc518b43c4b95dc4dce6906903eb5e09/common/sampling.cpp#L678)). For deterministic drafters such as n-gram, this greedy-match rule preserves the target distribution exactly at any temperature. The post-pin probabilistic verifier gained only 1 to 6% in accepted length and does not apply to n-gram drafters ([PR #27694](https://github.com/ggml-org/llama.cpp/pull/27694)). Onyx-specific rules follow from its design. A slot's verify rows must never be split across `decode_batch` views. `accept` runs only on emitted tokens, which keeps grammar, penalty and reasoning-budget state consistent. Logprobs come from the existing `compute_token_probs` on each accepted row, which upstream's pin left as a TODO. EOG and stop strings truncate an accepted run, a bug upstream fixed late ([#29638](https://github.com/ggml-org/llama.cpp/pull/29638)).

The first drafter is a prompt-lookup hash index over the slot's prompt plus its output, about 100 to 150 lines. Its value depends on a per-slot acceptance kill switch, which upstream lacks. N-gram drafting has measured anywhere from 182 to 814 tok/s on repeated code ([PR #19164](https://github.com/ggml-org/llama.cpp/pull/19164)) down to a 17% loss at 32% acceptance ([HF benchmark](https://victor-mtp-on-hf-endpoints.static.hf.space/index.html)). On hybrid models, setting `n_rs_seq` to the maximum draft length makes `seq_rm` rollback succeed for up to that many tokens, with no checkpoint replay ([PIN llama-memory-recurrent.cpp](https://github.com/ggml-org/llama.cpp/blob/9723942adc518b43c4b95dc4dce6906903eb5e09/src/llama-memory-recurrent.cpp#L193)). The parameter is marked experimental. A draft-model mode comes later and stays opt-in behind a speed probe, because on a fast GPU a 0.5B draft made a 7B target run at 0.27x its normal speed ([InventiveHQ](https://inventivehq.com/blog/llama-cpp-speculative-decoding-consumer-gpu)). MTP gives the best consumer single-stream wins, about 1.3 to 1.9x ([PR #22673](https://github.com/ggml-org/llama.cpp/pull/22673)). But its driver relies on hidden-state functions that exist only in the staging header, and upstream itself calls parallel MTP "highly suboptimal" ([PR #23269](https://github.com/ggml-org/llama.cpp/pull/23269)). Waiting for that API to reach `llama.h` costs less than chasing it on every bump.

## Conclusion

The research flips the usual intuition about dependencies. Linking upstream's convenience library looks like the low-maintenance choice. In practice `common/` is the part of llama.cpp with no changelog, no compatibility checker and the most removals, while the lower-level `llama.h` that Onyx would build on is the part upstream keeps stable and documents in its API changelog ([#9289](https://github.com/ggml-org/llama.cpp/issues/9289)). Owning thin code on `llama.h` means fewer breaking changes per bump, not more maintenance. The only real exceptions are the pieces Onyx copies and the staging header. That points to a simple standing rule: copy what is big and stable, write what is thin or fast-moving, and never build on `src/llama-ext.h` without a fallback.

The plan also separates two goals that are easy to conflate. Unlinking `common/` is mostly the chat-layer job. The performance wins, prefix caching on 2026's SWA and hybrid models and n-gram speculation on agent traffic, sit in Stages 2 and 4 and need almost nothing from `common/`. The owner can therefore collect most of the user-visible value within the first five weeks and treat the final unlink as a scheduled cleanup. Stage 3 can even stop at "copied engine, upstream parsers behind the seam" if new-model coverage starts to matter more than purity.
